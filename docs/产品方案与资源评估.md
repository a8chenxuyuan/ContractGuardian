# 合同卫士：产品方案与资源评估

> 本文档面向 HR 与管理层，重点说明产品价值、设计思路、技术方案和资源投入。尽量避免代码细节，侧重可理解的产品逻辑和可量化的投入估算。

---

## 一、需求分析

### 1.1 市场背景

企业日常经营中需要处理大量合同：劳动合同、采购合同、租赁合同、借款合同、股权转让协议、保密协议等。传统合同审查主要依赖法务人员逐条阅读，存在三个突出问题：

- **效率低**：一份普通合同审查往往需要 30 分钟到数小时，复杂合同可能需要数天；
- **成本高**：企业需要配备专职法务或外聘律师，人力成本持续上升；
- **标准不统一**：不同法务人员的经验和关注点不同，审查质量存在波动。

随着大语言模型技术的发展，AI 已经能够理解合同文本、识别法律风险、引用相关法条，为合同审查自动化提供了可能。

### 1.2 用户痛点

| 用户角色 | 核心痛点 |
|----------|----------|
| 中小企业管理者 | 没有专职法务，签合同靠经验判断，容易遗漏风险 |
| 企业法务人员 | 合同量大，时间紧，机械性审查占用大量精力 |
| 律师/法务团队 | 希望把初级审查交给 AI，自己专注于复杂谈判和争议解决 |
| HR/行政人员 | 经常需要处理劳动合同，但不熟悉劳动法的具体条款 |

### 1.3 目标用户

本产品主要面向两类用户：

1. **B 端企业客户**：中小型企业的法务、HR、采购、管理层，需要快速识别合同中的常见法律风险；
2. **专业服务机构**：律师事务所、法务外包公司，用 AI 做初筛，提升人效。

### 1.4 需求优先级

| 优先级 | 需求 | 说明 |
|--------|------|------|
| P0 | 合同上传与解析 | 支持 PDF、DOCX 等常见格式，提取条款文本 |
| P0 | AI 风险审查 | 自动识别高风险、中风险、低风险问题 |
| P0 | 风险报告 | 生成结构化的 PDF/Word 审查报告 |
| P1 | 法律依据 | 每个风险都给出对应的法律条文 |
| P1 | 修改建议 | 给出可执行的修改方案 |
| P1 | 对话追问 | 用户可就审查结果提问 |
| P2 | 人工复核 | 高风险项提示专家复核 |
| P2 | 多行业适配 | 针对特定行业的合规要求做扩展 |

## 二、产品设计思路

### 2.1 产品定位

**合同卫士**是一款基于大语言模型的智能合同审查助手。它的定位不是替代律师，而是替代"重复性、规则化"的初级合同审查工作，帮助用户在几分钟内获得一份有法律依据、有修改建议的审查报告。

产品核心价值可以概括为三句话：

- **看得懂**：支持常见合同格式，自动解析条款；
- **查得准**：基于法律原则和真实法条识别风险；
- **改得了**：不仅指出问题，还给出修改建议。

### 2.2 核心功能设计

#### 2.2.1 合同上传与解析

用户在前端上传合同文件，系统自动完成以下工作：

- **格式识别**：支持 PDF、DOCX 等格式，自动识别文件类型；
- **文本抽取**：把合同内容拆分成段落和条款，保留原文结构；
- **条款结构化**：识别合同中的章节、条款编号，建立条款之间的层级关系；
- **向量化存储**：把条款文本转换成向量，便于后续语义检索。

设计要点：

- 上传后要立即返回"解析中"状态，避免用户等待；
- 解析过程放在后台异步执行，完成后通过消息推送通知前端；
- 对扫描版 PDF，需要 OCR 能力，可作为后续增强功能。

#### 2.2.2 AI 智能审查

这是产品的核心功能。系统不是用单一模型直接读合同，而是采用"多 Agent 协同"的方式，模拟真实法务团队的审查流程：

- **信息提取**：先提取合同类型、当事人、关键日期等基础信息；
- **法律研究**：根据合同内容推断涉及的法律领域，检索相关法条；
- **风险审查**：逐条审查合同条款，识别违法、不公平、高风险内容；
- **缺失条款检查**：检查劳动合同等法定合同是否缺少必备条款；
- **公平性审查**：从整体上判断双方权利义务是否对等；
- **交叉引用检查**：发现合同前后条款是否存在冲突；
- **法条验证**：验证引用法条是否真实有效；
- **盲区扫描**：发现其他 Agent 可能遗漏的隐藏问题；
- **辩论校验**：对高风险项进行正反辩论，减少误报。

每个 Agent 负责一个专业方向，最终结果汇总成一份统一的风险清单。

设计要点：

- **先规则、后 LLM**：确定性红线（如违约金过高、利率超限）先用规则判断，减少 LLM 调用和不稳定因素；
- **多层过滤**：候选风险经过 CriticAgent 二次校验，过滤明显误报；
- **动态加速**：对明显合法的合同减少 LLM 调用，降低时间和成本。

#### 2.2.3 风险报告生成

审查完成后，系统生成结构化报告，包含：

- **风险总览**：高风险、中风险、低风险的数量统计；
- **风险列表**：每个风险的类型、等级、条款原文、原因说明；
- **法律依据**：对应法律条文原文；
- **修改建议**：可执行的修改方案，部分给出修改后文本；
- **人工复核提示**：哪些风险建议专家再确认。

报告支持导出为 PDF 和 Word，方便用户存档、转发或修改。

设计要点：

- 报告要分层展示，先给总览，再给细节；
- 高风险项优先展示，用颜色区分等级；
- 支持点击风险定位到合同原文对应位置。

#### 2.2.4 对话式追问

用户可以针对审查结果提问，例如：

- "试用期超长是什么意思？"
- "这条风险对应的法律条文是哪一条？"
- "应该怎么修改这个条款？"

系统基于本次审查结果作答，不回答与当前合同无关的问题。

设计要点：

- 必须基于审查结果回答，不能编造风险；
- 保留多轮对话上下文，能理解追问；
- 不预测司法判决，不推荐具体律师。

#### 2.2.5 人工复核流程

对于高风险、低置信度、跨条款组合等复杂风险，系统会标记"建议人工复核"，提示用户寻求专业法务或律师确认。

设计要点：

- AI 只做初筛，复杂决策保留人工最终判断；
- 复核项按优先级排序，方便专家高效处理；
- 复核结果可以反馈给系统，持续优化模型判断。

### 2.3 用户体验设计

#### 2.3.1 三步完成审查

产品使用流程尽量简化：

1. **上传合同**：拖拽或点击上传；
2. **等待审查**：系统异步处理，实时显示进度；
3. **查看报告**：在线预览或导出 PDF/Word。

#### 2.3.2 实时进度反馈

审查过程中，前端通过 Server-Sent Events 实时接收进度消息，用户可以看到当前处于哪个阶段、预计还剩多久。避免用户面对空白页面产生焦虑。

#### 2.3.3 低门槛理解

- 法律术语给出通俗解释；
- 风险原因结合具体条款说明；
- 修改建议给出可直接使用的文本。

### 2.4 差异化竞争优势

| 维度 | 传统法务审查 | 通用 AI 聊天工具 | 合同卫士 |
|------|--------------|------------------|----------|
| 速度 | 30 分钟到数小时 | 即时但缺乏系统性 | 几分钟内完成系统性审查 |
| 法律依据 | 依赖个人经验 | 可能编造法条 | 基于真实法条库和联网检索 |
| 误报控制 | 专业人员判断 | 容易过度敏感 | 规则 + Critic 多层过滤 |
| 修改建议 | 专业但耗时 | 泛泛而谈 | 针对具体条款给出可执行建议 |
| 审计追踪 | 人工记录 | 无 | 全程记录审查过程和依据 |

## 三、技术实现方案

### 3.1 系统架构

系统采用前后端分离架构，整体分为五层：

| 层级 | 主要组件 | 作用 |
|------|----------|------|
| 展示层 | Vue.js 前端 | 用户交互、文件上传、报告展示、对话追问 |
| 接入层 | FastAPI 后端 | RESTful API、身份认证、文件处理、SSE 推送 |
| 任务层 | Celery 异步任务 | 合同解析、审查等耗时任务 |
| 智能层 | 多 Agent 引擎 | 14 个专业 Agent 协同完成合同审查 |
| 数据层 | PostgreSQL + Redis + Qdrant | 持久化数据、消息队列、向量检索 |

### 3.2 多 Agent 协同引擎

这是系统的技术核心。我们不使用单一 LLM 直接读合同，而是把审查任务拆分给多个专业 Agent，每个 Agent 负责一个子任务。

#### 3.2.1 为什么用多 Agent

单一 LLM 直接审查合同存在几个问题：

- **上下文有限**：长合同容易超出 LLM 上下文窗口；
- **任务复杂**：审查涉及法律研究、风险识别、公平性判断、交叉引用等多个专业方向；
- **结果不稳定**：同一个模型前后判断可能不一致；
- **难以追溯**：不知道风险是怎么得出的。

多 Agent 架构把复杂任务拆分成可管理的子任务，每个 Agent 专注一件事，结果可组合、可追溯。

#### 3.2.2 8 阶段审查流水线

Coordinator 负责编排所有 Agent，按以下 8 个阶段执行：

1. **Route（路由）**：判断合同类型，选择审查策略；
2. **Preload（预加载）**：解析合同，提取 chunks 和条款结构；
3. **LegalResearch（法律研究）**：推断法律领域，检索相关法条；
4. **Execute（并行执行）**：多个 Agent 并行审查（风险、缺失条款、公平性、行业合规等）；
5. **Merge+Link（合并关联）**：合并结果，建立条款与风险之间的关系；
6. **LegalVerify（法条验证）**：验证引用法条是否真实有效；
7. **Debate（辩论）**：对高风险项进行正反辩论，减少误报；
8. **Triage（分流输出）**：整理最终结果，标记需要人工复核的项。

#### 3.2.3 关键 Agent 说明

| Agent | 作用 |
|-------|------|
| LegalResearchAgent | 动态推断法律领域，检索法条，生成审查清单 |
| RiskReviewAgent | 逐条审查条款，识别风险，集成 RedFlagDetector 和 CriticAgent |
| CriticAgent | 对候选风险做二次校验，过滤误报 |
| CrossReferenceAgent | 检查合同前后条款是否冲突 |
| LegalVerifyAgent | 验证引用法条的真实性 |
| DebateAgent | 对高风险项做正反辩论 |
| HumanReviewAgent | 判断哪些风险需要人工复核 |
| ChatAgent | 基于审查结果回答用户追问 |

### 3.3 法律知识检索

系统需要让审查结论有法可依，因此法律知识检索是关键能力。

#### 3.3.1 三层检索策略

对每个法律领域，按以下顺序检索：

1. **本地知识库**：优先查询 PostgreSQL / Qdrant 中已缓存的法条；
2. **精准联网检索**：如果 LLM 已经推断出具体法律名称和条款号，直接抓取该条原文；
3. **泛化联网检索**：用 Tavily 做 broader 搜索兜底。

#### 3.3.2 向量检索

使用 BGE-M3 模型把法条和合同条款转成向量，存储在 Qdrant 中。向量检索可以命中语义相关但关键词不同的内容，例如搜索"试用期上限"也能找到"劳动合同期限三个月以上不满一年的，试用期不得超过一个月"。

#### 3.3.3 缓存机制

- 法条按 `法律名称 + 条款号` 缓存，避免重复检索；
- 审查要点按法条缓存，同一法条多次出现直接复用；
- 联网搜索结果按 query 缓存，控制 API 调用成本。

### 3.4 风险检测与过滤

#### 3.4.1 红线检测

RedFlagDetector 基于法律原则做快速红线检测：

- **数值型红线**：日违约金 > 0.1%、一次性违约金 > 合同标的 30%、年利率 > 12%、试用期超过法定上限等；
- **语义型红线**：通过向量召回可能触犯的原则，再用轻量 LLM 判断，例如"自愿放弃社保""工伤概不负责"等。

#### 3.4.2 误报过滤

CriticAgent 用 15 条通用法律常识规则过滤常见误报，例如：

- "不得用于赌博"是合法限制，不是违法目的；
- 违约金与赔偿损失在中国法下可以并用；
- 未约定质量标准不等于排除质保（民法典有默认规则）。

规则无法确定时，再交给轻量 LLM Critic 判断。

#### 3.4.3 合法合同加速

对没有明显风险信号的合同：

- 跳过泛化联网检索；
- 跳过整体性 LLM 审查；
- 减少不必要的 LLM 调用。

这样既保证风险不被遗漏，又避免在简单合同上浪费资源。

### 3.5 实时进度推送

审查过程通常需要几分钟，系统通过 Server-Sent Events（SSE）向前端推送进度：

- 当前处于哪个阶段；
- 已发现多少风险；
- 是否出现异常。

AgentBus 通过 Redis Pub/Sub 广播事件，确保异步 Worker 和前端实时同步。

### 3.6 前端交互

前端采用 Vue.js + Element Plus 构建，主要页面包括：

- **登录/注册页**：支持邮箱密码登录；
- **合同列表页**：展示所有上传的合同及审查状态；
- **审查详情页**：左侧预览合同原文，右侧展示风险列表和报告；
- **报告页**：展示完整审查报告，支持导出 PDF/Word；
- **对话页**：基于审查结果进行多轮问答。

设计要点：

- 左侧文档预览支持 PDF 和 DOCX；
- 右侧风险卡片按等级分色展示；
- 点击风险可定位到原文对应位置。

### 3.7 数据存储

| 数据 | 存储方案 | 原因 |
|------|----------|------|
| 用户信息、合同元数据、审查会话 | PostgreSQL | 关系型数据，需要事务支持 |
| 异步任务队列、实时消息 | Redis | 高性能缓存和 Pub/Sub |
| 法条和合同条款向量 | Qdrant | 专用向量数据库，支持语义检索 |
| 合同文件 | 本地文件系统 / 对象存储 | 大文件不适合存数据库 |

### 3.8 安全与扩展性

#### 3.8.1 安全

- 用户认证使用 JWT，接口做权限校验；
- 合同文件按用户隔离存储；
- 敏感配置（API Key、数据库密码）通过环境变量管理；
- LLM 输出做风险等级校验，防止非标准值流入下游。

#### 3.8.2 扩展性

- Agent 可插拔：新增 Agent 只需注册到 Coordinator；
- 法律知识库可扩展：新增行业法规只需导入向量库；
- 模型可替换：LLM 通过统一接口调用，可切换不同模型；
- 支持水平扩展：Celery Worker 可部署多台机器分担任务。

### 3.9 RAG：检索增强生成

RAG（Retrieval-Augmented Generation，检索增强生成）是本系统的核心技术之一。简单理解，就是让 LLM 在回答问题之前，先查阅相关资料，再基于资料作答，而不是完全依赖模型自身的记忆。

#### 3.9.1 为什么需要 RAG

大语言模型有两个明显局限：

- **知识有截止日期**：模型训练数据截止到某个时间点，之后的法律法规更新它不知道；
- **容易编造**：法学领域对准确性要求极高，模型可能"一本正经地胡说八道"，虚构不存在的法条。

RAG 的解决思路是：在 LLM 回答之前，先从知识库中检索出相关法律条文和类似条款，把这些真实资料放进问题上下文，让 LLM 基于资料作答。这样既保证了时效性，也大大降低了编造风险。

#### 3.9.2 两层检索架构

系统的 RAG 分为两层：

**第一层：向量语义检索**

使用 BGE-M3  embedding 模型，把用户查询和知识库中的法条都转成 1024 维向量。当用户查询"试用期上限"时，系统不是去数据库里匹配"试用期"三个字，而是在向量空间中找到语义相近的内容，例如"劳动合同期限三个月以上不满一年的，试用期不得超过一个月"。

向量检索的优势是能理解同义表达和语义关联，例如"加班费"也能命中"工资报酬"相关的法条。

**第二层：关键词检索降级**

如果向量数据库不可用、模型加载失败，或者向量检索结果为空，系统会自动降级到 SQL 关键词检索。它会在 PostgreSQL 中用 LIKE 匹配法律名称、条款号、标题和正文，保证系统在服务异常时仍有基本检索能力。

#### 3.9.3 RAG 在审查流程中的应用

RAG 主要在两个环节发挥作用：

- **LegalResearchAgent 阶段**：根据合同内容检索相关法律，为后续审查提供法律依据；
- **RiskReviewAgent / LegalBasisAgent 阶段**：为已发现的风险补充对应的法条原文。

#### 3.9.4 检索质量优化

为了提高检索准确率，系统做了以下优化：

- **混合检索**：向量检索 + 关键词检索互补，覆盖语义相似和精确匹配两种场景；
- **结果过滤**：对检索到的法条做相关性判断，过滤与当前法律领域无关的内容；
- **去重合并**：同一法条可能同时被向量和关键词检索命中，按法律名称和条款号去重；
- **缓存复用**：已检索过的法条和查询结果会被缓存，避免重复调用。

### 3.10 法律知识库构建

法律知识库是 RAG 的资料来源，也是系统能够"有法可依"的基础。

#### 3.10.1 知识库内容来源

法律知识库主要包括三类内容：

- **基础法律法规**：如《民法典》《劳动合同法》《劳动法》《社会保险法》等；
- **司法解释和指导案例**：如民间借贷司法解释、劳动争议司法解释等；
- **行业特定法规**：如金融、医药、建筑、互联网等行业的特殊合规要求。

#### 3.10.2 知识库构建流程

构建知识库一般分为以下步骤：

1. **法条清洗**：把原始法律文本按"法律名称 + 条款号 + 条款内容"的结构化形式拆分；
2. **向量化**：用 BGE-M3 模型把每条法条转成向量；
3. **入库**：把向量、原文和元数据写入 Qdrant 向量库，同时保留一份在 PostgreSQL 中做关键词检索备份；
4. **缓存管理**：对联网检索到的法条按"法律名称 + 条款号"缓存，避免重复抓取。

#### 3.10.3 知识库维护与扩展

- **增量更新**：新增法律或修订条文时，只需要导入新增部分，不需要重建整个库；
- **版本管理**：记录法条的有效性状态，便于 LegalVerifyAgent 检查法条是否被废止；
- **行业扩展**：针对新行业，导入该行业的专门法规，并在 Agent 中增加对应的审查重点。

#### 3.10.4 知识库与 LLM 的关系

可以把知识库理解成 LLM 的"外部记忆"。LLM 负责理解和推理，知识库负责提供准确、可溯源的法律资料。两者结合，既发挥了 LLM 的语义理解能力，又避免了它编造法条的问题。

### 3.11 记忆层设计

记忆层解决的是"多个 Agent 之间如何共享信息"的问题。系统中有十几个 Agent，如果每个 Agent 都孤立运行，就无法基于其他 Agent 的发现做综合判断。

#### 3.11.1 记忆层的两层结构

系统的记忆层分为两层：

**第一层：SessionGraph（会话图）**

SessionGraph 是当前合同审查会话的"工作底稿"。它以图的形式存储审查过程中产生的所有实体和关系：

- **Clause 节点**：合同的段落和条款；
- **Law 节点**：检索到的法律法条；
- **Risk 节点**：发现的风险；
- **Term 节点**：提取的关键信息（如当事人、金额、日期）；
- **边**：表示实体之间的关系，例如 Clause 到 Risk 的"HAS_RISK"、Risk 到 Law 的"BASED_ON"。

所有 Agent 都可以读写 SessionGraph，实现信息共享。例如 LegalResearchAgent 写入 Law 节点，RiskReviewAgent 读取 Law 节点作为法律依据，CrossReferenceAgent 读取 Clause 节点检查冲突。

**第二层：AgentBus（事件总线）**

AgentBus 负责把审查过程中的事件实时广播出去，例如"当前进入 LegalResearch 阶段""已发现 3 个风险"。这些事件通过 Redis Pub/Sub 发送，前端可以订阅并展示进度。

AgentBus 和 SessionGraph 的区别：

- SessionGraph 存储的是"审查结果和中间数据"；
- AgentBus 传输的是"进度事件和状态变更"。

#### 3.11.2 记忆层的工作方式

一个典型的信息共享场景：

1. PreloadAgent 解析合同，生成 Clause 节点；
2. LegalResearchAgent 检索法条，生成 Law 节点；
3. RiskReviewAgent 读取 Clause 和 Law，生成 Risk 节点，并建立 Clause→Risk 关系；
4. LegalBasisAgent 读取 Risk，补充 Law 引用；
5. CrossReferenceAgent 读取 Clause 节点，发现跨条款冲突；
6. BlindSpotAgent 读取所有已有 Risk，发现遗漏风险；
7. HumanReviewAgent 读取所有 Risk，判断哪些需要人工复核；
8. ChatAgent 读取 Risk 和 Clause，回答用户追问。

#### 3.11.3 记忆层的价值

- **可追溯**：每个风险都能追溯到具体条款和法律依据；
- **可协作**：多个 Agent 基于同一份"工作底稿"协同工作；
- **可解释**：审查过程不是黑盒，可以查看每个阶段产生了什么；
- **可复用**：会话完成后，图数据可以保存，用于后续分析和模型优化。

### 3.12 Agent 关系与协作流程

系统中的 14 个 Agent 不是简单串联，而是按照 8 阶段流水线协作，不同阶段调用不同 Agent，部分 Agent 可以并行执行。

#### 3.12.1 8 阶段流水线总览

```
Route → Preload → LegalResearch → Execute → Merge+Link → LegalVerify → Debate → Triage
```

| 阶段 | 参与的 Agent | 主要工作 |
|------|--------------|----------|
| Route | RouteAgent | 判断合同类型，确定审查策略 |
| Preload | PreloadAgent | 解析合同文本，生成 Clause 节点 |
| LegalResearch | LegalResearchAgent | 推断法律领域，检索法条，生成审查清单 |
| Execute | RiskReviewAgent、MissingClauseAgent、BalanceAgent、IndustryComplianceAgent、CrossReferenceAgent | 并行执行各类审查任务 |
| Merge+Link | Coordinator | 合并结果，建立节点关系 |
| LegalVerify | LegalBasisAgent、LegalVerifyAgent | 补充并验证法律依据 |
| Debate | DebateAgent | 对 high 风险正反辩论 |
| Triage | HumanReviewAgent、Coordinator | 整理输出，标记人工复核项 |

#### 3.12.2 串行与并行关系

- **串行阶段**：Route、Preload、LegalResearch、Merge+Link、LegalVerify、Debate、Triage 必须按顺序执行，前一阶段的结果是后一阶段的输入；
- **并行阶段**：Execute 阶段内的多个 Agent（RiskReview、MissingClause、Balance、IndustryCompliance、CrossReference）可以并行运行，互不阻塞，最后由 Coordinator 合并结果。

#### 3.12.3 Agent 之间的数据依赖

| 上游 Agent | 下游 Agent | 依赖内容 |
|------------|------------|----------|
| PreloadAgent | LegalResearchAgent、RiskReviewAgent | 合同 chunks、Clause 节点 |
| LegalResearchAgent | RiskReviewAgent | discovered_laws、review_checklist、risk_signals |
| RiskReviewAgent | LegalBasisAgent、LegalVerifyAgent、DebateAgent、HumanReviewAgent | Risk 节点 |
| CrossReferenceAgent | BlindSpotAgent、HumanReviewAgent | Clause 之间的关系、跨条款风险 |
| LegalBasisAgent | LegalVerifyAgent | Risk 的 law_refs |
| 所有产生 Risk 的 Agent | HumanReviewAgent | 完整 Risk 列表 |

#### 3.12.4 为什么这样设计

- **专业化**：每个 Agent 只负责一个领域，Prompt 和逻辑可以更聚焦；
- **可替换**：某个 Agent 升级或替换不会影响整体流程；
- **可扩展**：新增一种审查维度（如税务合规），只需新增一个 Agent 并注册到 Execute 阶段；
- **容错性**：单个 Agent 失败不会导致整个审查流程崩溃，Coordinator 可以跳过或降级处理。

### 3.13 各 Agent 详细说明

下面逐个说明每个 Agent 的职责、输入、处理和输出。

#### 3.13.1 RouteAgent（路由 Agent）

**职责**：判断合同类型（如劳动合同、借款合同、租赁合同），决定后续使用哪些审查策略和 Agent。

**输入**：合同标题、前几句文本。

**处理**：用 LLM 或关键词匹配识别合同类型。

**输出**：contract_type，供后续 Agent 使用。

#### 3.13.2 PreloadAgent（预加载 Agent）

**职责**：解析合同文件，提取文本，拆分成 chunks，建立条款层级结构。

**输入**：上传的合同文件。

**处理**：PDF 用 pdf.js 解析，DOCX 用文档解析库提取文本，按段落拆分，识别章节标题。

**输出**：chunks 列表、section_tree 章节树、Clause 节点。

#### 3.13.3 LegalResearchAgent（动态法律研究 Agent）

**职责**：在正式审查前做好法律功课，推断合同涉及哪些法律领域，检索相关法条，生成审查清单。

**输入**：合同 chunks、contract_type。

**处理**：
1. 拼接合同摘要；
2. 一次 LLM 调用推断法律领域和风险信号；
3. 分层检索法条（本地库 → 精准联网 → 泛化联网）；
4. 生成审查要点；
5. 写入 Law 节点；
6. 生成动态审查清单。

**输出**：discovered_laws、review_checklist、risk_signals。

#### 3.13.4 RiskReviewAgent（风险审查 Agent）

**职责**：合同审查的主审律师，逐条审查条款，识别风险。

**输入**：chunks、discovered_laws、review_checklist、risk_signals。

**处理**：
1. RedFlagDetector 红线扫描；
2. 关键词过滤；
3. LLM 审查；
4. 红线兜底覆盖；
5. CriticAgent 二次校验；
6. 整体性审查。

**输出**：Risk 节点（包含风险类型、等级、原因、建议、法条引用）。

#### 3.13.5 MissingClauseAgent（缺失条款 Agent）

**职责**：检查劳动合同是否缺少《劳动合同法》第 17 条规定的必备条款。

**输入**：合同全文。

**处理**：对照法定必备条款清单，让 LLM 判断缺少哪些。

**输出**：缺失条款类 Risk 节点。

#### 3.13.6 BalanceAgent（公平性 Agent）

**职责**：从全局视角审视合同双方权利义务是否对等。

**输入**：合同全文。

**处理**：让 LLM 横向对比甲乙双方的权利义务分配。

**输出**：公平性类 Risk 节点。

#### 3.13.7 CrossReferenceAgent（交叉引用 Agent）

**职责**：检查合同前后条款是否冲突。

**输入**：所有 Clause 节点。

**处理**：识别潜在关联条款对，用规则检查是否冲突（如试用期与合同期限、社保放弃与工资条款）。

**输出**：跨条款冲突类 Risk 节点，Clause 之间的关系边。

#### 3.13.8 LegalBasisAgent（法律依据 Agent）

**职责**：为已发现的风险补充法律依据。

**输入**：Risk 节点。

**处理**：根据风险类型构造关键词，检索法律知识库。

**输出**：更新 Risk 节点的 law_refs 字段。

#### 3.13.9 LegalVerifyAgent（法条验证 Agent）

**职责**：验证 Risk 引用的法条是否真实、准确、有效。

**输入**：带 law_refs 的 Risk 节点。

**处理**：在知识库中精确匹配法条编号和内容，检查是否被废止或更新。

**输出**：更新 Risk 节点的 verified 字段，验证失败的降低置信度。

#### 3.13.10 SuggestionAgent（修改建议 Agent）

**职责**：为风险生成具体可执行的修改建议。

**输入**：Risk 节点。

**处理**：批量汇总风险，调用 LLM 为每个风险输出原文、修改后文本、修改理由。

**输出**：更新 Risk 节点的 suggestion 字段。

#### 3.13.11 IndustryComplianceAgent（行业合规 Agent）

**职责**：识别特定行业的特殊合规风险。

**输入**：合同全文、contract_type、industry。

**处理**：LLM 按行业合规重点审查，规则兜底检查明显违法表述。

**输出**：行业合规类 Risk 节点。

#### 3.13.12 DebateAgent（辩论 Agent）

**职责**：对 high 风险进行正反辩论，减少误报。

**输入**：high 等级的 Risk 节点（最多 5 个）。

**处理**：分别论证"这是风险"和"这不是风险"，给出保留/降级/撤销结论。

**输出**：辩论结论写回 Risk 节点，Triage 阶段应用。

#### 3.13.13 BlindSpotAgent（盲区扫描 Agent）

**职责**：从全局视角发现其他 Agent 遗漏的风险。

**输入**：所有 Risk 节点、所有 Clause 节点。

**处理**：让 LLM 在已知结果基础上发现隐藏问题，规则检查"有主题无配套约定"的情况。

**输出**：盲区类 Risk 节点。

#### 3.13.14 HumanReviewAgent（人工复核 Agent）

**职责**：判断哪些风险需要人工专家复核。

**输入**：所有 Risk 节点。

**处理**：按风险等级、置信度、是否跨条款、是否缺少法条等维度判断。

**输出**：人工复核项列表，按优先级排序。

#### 3.13.15 CriticAgent（二次校验 Agent）

**职责**：对 RiskReviewAgent 提出的候选风险做二次校验，过滤误报。

**输入**：RiskReviewAgent 产生的候选风险。

**处理**：先用 15 条通用法律常识规则快速判断，不确定时走 LLM Critic。

**输出**：明确误报过滤、边界情况交给 LLM、有效风险保留。

#### 3.13.16 ChatAgent（对话 Agent）

**职责**：基于审查结果回答用户追问。

**输入**：用户问题、对话历史、SessionGraph 中的审查结果。

**处理**：导出图中的关键风险和条款，构造 Prompt 生成回答。

**输出**：回答内容、引用的风险类型。

## 五、总结

合同卫士通过"多 Agent 协同 + 法律知识库 + 规则过滤"的技术方案，把传统需要数小时的合同审查压缩到几分钟，同时保证审查结果有法可依、有据可查。

产品当前已完成 MVP 核心功能，接下来重点是：

1. **提升准确率**：持续优化 Agent 协作和误报过滤；
