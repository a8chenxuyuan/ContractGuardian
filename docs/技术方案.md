## 二、项目概述

### 2.1 产品定位

"合同卫士"是一款面向个人用户与中小企业的专业级 AI 合同审查助手。用户上传劳动合同后，系统自动解析合同文本、识别风险条款、解释法律含义、给出修改建议，并以结构化报告的形式呈现，支持原文高亮、多格式导出、交互式追问和人工复核。

### 2.2 核心场景

系统以**劳动合同审查**为核心场景。劳动合同具有以下特点：

- 法律法规相对明确，主要依据《劳动合同法》《劳动法》及相关司法解释；
- 合同条款结构相对固定，便于建立标准化审查模板；
- 风险类型集中，如试用期、违约金、竞业限制、工作地点、社保缴纳等；
- 个人用户和小企业需求强烈，市场验证成本低。

同时，系统架构预留扩展能力，未来可平滑支持租房合同、服务合同、借款合同、买卖合同等其他高频合同类型。

### 2.3 核心差异点

与通用文档 AI 工具相比，本产品的核心差异包括：

- **结构化风险审查**：不是简单给出一段总结，而是逐条输出风险类型、等级、法律依据、修改建议；
- **原文高亮定位**：每条风险都能追溯到合同原文的具体位置；
- **多 Agent 并行审查**：多个专业 Agent 分别从不同维度审查合同，结论可交叉验证；
- **法律知识库驱动**：引用真实法规与案例，结果可追溯；
- **人机协同复核**：低置信度风险项可转人工复核；
- **知识持续沉淀**：通过 Knowledge Curator 自动整理审查经验，系统越用越准。

## 三、技术栈总览

### 3.1 选型原则

技术栈选型遵循以下原则：

- **完整性**：从项目一开始就构建最终产品所需的技术底座；
- **开发效率**：选择生态成熟、文档丰富、团队熟悉度高的技术；
- **AI 生态友好**：Agent 开发需要丰富的 LLM、向量检索、提示工程工具支持；
- **可扩展性**：架构支持未来多合同类型、企业版、私有化部署；
- **可维护性**：技术栈统一，模块边界清晰，便于长期维护。

### 3.2 各层技术选型

| 层级 | 技术选择 | 说明 |
|------|---------|------|
| 前端框架 | Vue 3 + TypeScript | 组件化开发，类型安全 |
| 后端框架 | FastAPI（Python） | 异步性能优秀，AI/Agent 生态成熟，开发效率高 |
| 数据库 | PostgreSQL | 关系型数据稳定，JSONB 支持存储结构化审查结果 |
| 缓存与队列 | Redis | 统一承担缓存、任务队列、分布式锁职责 |
| 异步任务 | Celery + Redis | 合同审查是耗时操作，需要异步执行 |
| 向量数据库 | Qdrant | 支持合同内语义搜索和法律知识库检索，生产级可扩展 |
| 图数据库 | Neo4j | 构建法规-条款-案例知识图谱，支持跨实体关系查询 |
| 文档解析 | python-docx + PyMuPDF + PaddleOCR | 覆盖 Word、PDF、图片三种常见格式 |
| 向量嵌入 | BGE-M3 | 中文语义理解能力强，支持本地部署 |
| LLM | 通义千问 / DeepSeek | 国内模型优先，成本低，劳动合同场景法规明确 |
| Agent 框架 | 自定义 Coordinator + 自定义 ReAct | Coordinator 管理八阶段状态流转，自定义 ReAct 控制工具调用 |
| PDF 展示 | pdf.js | 浏览器端渲染 PDF，支持高亮和滚动定位 |
| 报告生成 | WeasyPrint + python-docx | 生成 PDF 和 Word 报告 |
| 部署 | Docker + Kubernetes + 云服务 | 容器化部署，便于扩展和私有化 |

### 3.3 关键取舍说明

#### 3.3.1 为什么后端选 Python / FastAPI？

Python 在 LLM Agent、向量检索、提示工程等方向的库和框架最为丰富。FastAPI 异步性能优秀，与 Celery、SQLAlchemy、Pydantic 配合成熟，能够快速构建生产级后端服务。

#### 3.3.2 为什么用 Qdrant 作为向量数据库？

项目从一开始就构建完整法律知识库，需要对大量法规、案例、合同条款进行语义检索。Qdrant 是生产级的向量数据库，支持高密度向量、过滤查询、混合检索，能够满足合同内搜索和法律知识库搜索双重需求。

#### 3.3.3 为什么用 Neo4j 作为图数据库？

法律知识不是孤立的文本，法规、条款、案例、风险类型之间存在复杂关系。Neo4j 能够高效表达和查询这些关系，支持"某条法规关联哪些案例""某类风险通常涉及哪些条款"等图遍历查询，是实现 Knowledge Curator 和深度法律推理的基础。

#### 3.3.4 为什么 Agent 框架用自定义 Coordinator + 自定义 ReAct？

- 合同审查管线需要精确控制八阶段执行顺序、阶段内并行策略和条件化跳过逻辑（如 LegalResearch 快速路径、holistic review 条件触发、跨条款 LLM 兜底），自定义 Coordinator 比通用框架更直接可控；
- 纯框架化的 Agent 方案灵活性不足，难以精确控制每个 Agent 的 ReAct 轮次、工具集和输出格式；
- 自定义 ReAct 可以在标准 ReAct 循环基础上加入风险分级、动态升降级、SessionGraph 写入、AgentBus 广播等定制逻辑；
- 当前实现不依赖 LangChain / LangGraph，未来若 Agent 数量和流程复杂度进一步增加，可考虑引入 LangGraph 做状态管理。

### 4.2 数据流向

用户上传合同后，数据按以下顺序流转：

1. 文件进入对象存储，并在 `contracts` 表中创建记录；
2. Celery 启动解析任务，文档解析引擎生成 Section 树、Chunk 列表、向量索引；
3. Chunk 向量存入 Qdrant，用于合同内语义搜索；
4. Coordinator 创建 SessionGraph，启动多个 Agent 并行审查；
5. Agent 在 ReAct 循环中调用工具，通过 `search_knowledge` 查询 Qdrant/Neo4j 法律知识库，必要时联网搜索；
6. Agent 发现风险后写入 SessionGraph，并通过 AgentBus 广播高风险发现；
7. Coordinator 执行合并、去重、验证、辩论、分流，生成最终风险列表；
8. 报告服务将风险列表渲染为前端可展示的格式；
9. 前端通过 SSE 接收实时进度，审查完成后展示报告；
10. 审查会话结果持久化到 PostgreSQL，高风险/低置信度项进入人工复核队列；
11. Knowledge Curator 定期整理审查中产生的新知识，经去重和时效性检查后写入 Qdrant 和 Neo4j；
12. ChatAgent 基于 SessionGraph 和合同原文回答用户追问。

### 5.3 文档解析引擎

#### 5.3.1 职责

文档解析引擎负责把用户上传的合同文件转换为 Agent 可以消费的结构化数据。它是 AI 审查引擎的前置依赖，输出的质量直接影响后续审查效果。

#### 5.3.2 处理流程

1. **格式统一**：如果是 Word 文件（.doc/.docx），先转换为 PDF；
2. **文本提取**：从 PDF 中提取文本、单词坐标、段落块、表格；
3. **文本清洗**：合并中文空格、压缩连续空格、处理乱码；
4. **章节识别**：识别合同标题和条款层级，构建 Section 树；
5. **Chunk 切分**：把合同切分为语义完整的条款片段；
6. **向量化**：使用 BGE-M3 生成向量，存入 Qdrant。

#### 5.3.3 技术实现

- **python-docx**：读取 Word 文件文本和段落结构；
- **PyMuPDF（fitz）**：从 PDF 提取文本和页面坐标；
- **PaddleOCR**：对图片或扫描件进行文字识别；
- **LibreOffice headless**：复杂 Word 排版时转换为 PDF（备选）；
- **BGE-M3**：生成 1024 维向量；
- **Qdrant Client**：将向量写入 Qdrant collection。

#### 5.3.4 输出数据结构

文档解析引擎的输出包括：

- **RawDocument**：原始提取结果，包含页面、单词、段落块、表格及其坐标；
- **Section 树**：嵌套的章节结构，每个节点包含标题、正文、页码范围、block 引用；
- **Chunk 列表**：条款级语义片段，每个 Chunk 包含文本、页码、来源 block ID、层级路径；
- **Qdrant Collection**：以合同为单位的向量集合，支持语义搜索。

### 5.5 报告与交互层

#### 5.5.1 职责

报告与交互层负责把 Agent 的审查结果转化为用户可理解、可操作的界面内容。它不是简单拼接文本，而是需要对风险进行聚合、分级、去重、排序，并生成前端友好的数据结构。

#### 5.5.2 技术实现

- 使用 Python 在服务端完成风险聚合和排序；
- 使用 Pydantic 模型定义报告数据结构；
- 使用 **WeasyPrint** 生成 PDF 报告；
- 使用 **python-docx** 生成 Word 报告；
- ChatAgent 基于 BaseAgent 实现，消费 SessionGraph 和合同原文。

#### 5.5.3 信息架构

前端报告采用四层金字塔结构：

- **L0 全局状态条**：显示审查进度、风险总数、高中低风险数量；
- **L1 风险卡片**：默认展示，包含风险类型、条款、置信度、法律依据摘要；
- **L2 推理摘要**：点击展开后显示风险原因、法律依据、修改建议、审查路径；
- **L3 完整 ReAct 日志**：按需查看 Agent 的完整思考过程，用于审计追溯。

### 5.6 数据与知识层

#### 5.6.1 职责

数据与知识层负责全系统的数据持久化、缓存、任务队列和知识支撑。

#### 5.6.2 PostgreSQL 数据库设计

核心表包括：

- `users`：用户表
- `memberships`：会员信息表
- `contracts`：合同基本信息表
- `contract_files`：合同文件存储信息表
- `review_sessions`：审查会话表，包含 SessionGraph、风险结果、统计信息
- `findings`：风险发现表，用于细粒度查询和统计
- `chat_records`：对话记录表
- `payments`：支付订单表
- `human_reviews`：人工复核记录表
- `knowledge_articles`：法律法规条目表
- `knowledge_cases`：典型案例表
- `knowledge_templates`：标准范本表

#### 5.6.3 Redis 用途

- Celery 任务队列；
- JWT Token 黑名单；
- 审查状态缓存；
- 搜索结果缓存；
- 分布式锁（防止同一合同被重复审查）。

#### 5.6.4 Qdrant 向量数据库

Qdrant 用于存储两类向量数据：

- **合同内 Chunk 向量**：每个合同上传后生成一个 collection，支持 Agent 在合同内语义搜索；
- **法律知识库向量**：法规条款、案例、范本、风险模式等，支持 `search_knowledge` 工具检索。

#### 5.6.5 Neo4j 图数据库

Neo4j 用于存储法律知识图谱，节点类型包括：

- Law（法规）
- Article（条款）
- Case（案例）
- RiskPattern（风险模式）
- Dimension（审查维度）
- ProhibitionRule（负面清单）

关系类型包括：

- `CONTAINS`：法规包含条款
- `BASED_ON`：案例依据某条款
- `TRIGGERS`：风险模式触发某风险
- `RELATED_TO`：条款之间相互关联
- `CONTRADICTS`：条款之间相互冲突

#### 5.6.6 法律知识库

法律知识库包括：

- 《中华人民共和国劳动合同法》全文及司法解释；
- 《中华人民共和国劳动法》相关条款；
- 《中华人民共和国公司法》相关条款；
- 《中华人民共和国劳动争议调解仲裁法》相关条款；
- 最高人民法院关于劳动争议案件的司法解释（一）（二）（三）；
- 各地最低工资标准、社保缴纳规定、劳动仲裁规则；
- 典型案例、标准范本、负面清单。

法律知识通过 Qdrant 进行语义检索，通过 Neo4j 进行关系遍历，通过 PostgreSQL 进行元数据管理。

## 六、Agent 部分详细说明

### 6.1 Agent 整体架构

AI 审查引擎采用 **Multi-Agent 协作架构**。不是用一个通用大模型直接审完整份合同，而是把审查任务拆分为多个子任务，每个子任务由一个专业 Agent 负责。这些 Agent 并行工作，共享同一个 SessionGraph，最终由 Coordinator 汇总结果。

这种架构的优势在于：

- **专业化**：每个 Agent 只关注一类问题，Prompt 更聚焦，审查质量更高；
- **可解释性**：每个风险都能追溯到具体是哪个 Agent 发现的；
- **可扩展性**：新增审查维度只需增加一个 Agent；
- **交叉验证**：同一条款可能被多个 Agent 审查，减少漏判和误判；
- **持续进化**：BlindSpotAgent 可以发现新的风险模式，建议生成 Dynamic Agent。

### 6.2 Coordinator 八阶段管线

Coordinator 是 AI 审查引擎的调度中心，负责控制整个审查流程。它把审查过程拆分为八个阶段：

```
Route → Preload → LegalResearch → Execute → Merge+Link → LegalVerify → Debate → Triage
```

#### 6.2.1 Route（路由）

Coordinator 读取解析后的 Chunk 列表，根据每个 Chunk 的内容特征，决定派发给哪些 Agent 审查，并分配初始风险等级（`high` / `medium` / `low`）。风险等级与项目输出规范保持一致，避免后续转换歧义。

例如：

- 包含"试用期""违约金""社保""竞业限制"等明确信号的词，派给 RiskReviewAgent、BalanceAgent、LegalBasisAgent，并标记为 `high`；
- 包含"工资""解除""工作地点""保密"等需要进一步确认的词，派给 RiskReviewAgent 和 BalanceAgent，并标记为 `medium`；
- 格式性、通用性条款默认只过 RiskReviewAgent 和 MissingClauseAgent，标记为 `low`。

Route 阶段当前采用关键词初筛，预留了 BGE-M3 向量相似度辅助分级的扩展接口。

#### 6.2.2 Preload（预加载）

在 Agent 开始审查前，Coordinator 预加载共享上下文：

- 整个合同的 Section 树；
- Qdrant 中的合同 Chunk 向量索引；
- 基础法律知识片段（如劳动合同法第 19 条、第 22 条等）；
- 历史相似审查结果（如果有）。

预加载的目的是减少 Agent 在 ReAct 循环中重复搜索的次数。

#### 6.2.3 Execute（执行）

多个 Agent 并行审查各自被分配的 Chunk。每个 Agent 内部是一个独立的 ReAct 循环，可以调用工具查询法规、搜索合同内相似条款、读取其他条款等。

Agent 在审查过程中会把发现的风险写入 SessionGraph，并通过 AgentBus 向其他 Agent 广播高风险发现。

#### 6.2.4 Merge+Link（合并与关联）

所有 Agent 执行完毕后，Coordinator 对 SessionGraph 进行后处理：

- **去重**：采用**法律指纹（legal fingerprinting）**先把同一法律问题的不同表述归一化，再在组内通过 clause_text 包含关系、2-gram Jaccard 相似度、clause_ids 交集判断是否重复，合并为一条；
- **关联**：发现跨条款组合风险，例如"试用期 6 个月"与"合同期限 2 年"组合违法；
- **LLM 兜底**：当配置驱动规则已命中组合风险，或图中已存在 `high`/`medium` 风险时，才调用 LLM 补充未发现的风险，避免在明显合法的合同上浪费一次 LLM 调用；
- **分级调整**：合并时保留最高风险等级和最高置信度。

#### 6.2.5 LegalVerify（法条验证）

LegalVerifyAgent 对所有已发现风险的法律依据进行验证：

- 检查引用的法条是否存在于法律知识库；
- 检查法条引用是否准确；
- 对存疑的法条重新搜索确认；
- 标记无法验证的风险，降低其置信度或转人工复核。

这一步骤可以降低模型"编造法条"的风险。

#### 6.2.6 Debate（正反辩论）

对于高风险或置信度不高的发现，DebateAgent 进行正反辩论：

- 正方：论证这确实是风险；
- 反方：论证这可能不是风险，或存在例外情况；
- 最终由 Coordinator 根据辩论结果决定是否保留、调整等级或撤销。

Debate 机制可以有效降低误判率。

#### 6.2.7 Triage（分流输出）

最后，Coordinator 把所有风险分为三类：

- **🔴 必须改**：明确违法或严重不公平；
- **🟡 需复核**：有风险嫌疑，但需要人工确认；
- **🟢 优化建议**：不违法，但可以写得更规范。

同时，低置信度风险、Agent 意见冲突项、组合风险等会进入 HumanReviewAgent 的人工复核队列。

### 6.3 ReAct 循环

#### 6.3.1 什么是 ReAct

ReAct 是一种让大模型通过"思考-行动-观察"循环完成任务的方法。每个循环包含三步：

1. **Thought（思考）**：Agent 根据当前信息决定下一步做什么；
2. **Action（行动）**：Agent 调用一个工具，例如搜索法规、读取条款；
3. **Observation（观察）**：Agent 获得工具返回结果，更新认知。

循环重复进行，直到 Agent 认为已经掌握足够信息，输出最终结论。

#### 6.3.2 为什么用 ReAct

劳动合同审查不是一次性问答可以完成的。Agent 需要：

- 先读条款，判断可能存在什么问题；
- 再搜索相关法律；
- 再比对合同其他相关条款；
- 最后才能下结论。

ReAct 让 Agent 能够像人一样"边查边想"，而不是一次性生成结论。

#### 6.3.3 ReAct 循环示例

以审查"试用期 6 个月"条款为例：

**Turn 1：**
- Thought：这条款约定试用期 6 个月，需要确认是否超过法定上限。
- Action：调用 `search_knowledge("劳动合同法 试用期 最长期限")`。
- Observation：《劳动合同法》第 19 条规定，三年以上固定期限劳动合同，试用期不得超过六个月。

**Turn 2：**
- Thought：试用期上限取决于合同期限。需要查找本合同的期限条款。
- Action：调用 `search_document("合同期限")`。
- Observation：合同期限为 2 年。

**Turn 3：**
- Thought：2 年期限的劳动合同，试用期最长为 2 个月。本合同约定 6 个月，违法。
- Action：调用 `output_finding(...)` 输出风险发现。
- Observation：风险已写入 SessionGraph。

### 6.4 Agent 工具集

Agent 在 ReAct 循环中可以调用以下工具：

#### 6.4.1 通用工具

| 工具名 | 功能 | 使用场景 |
|--------|------|---------|
| `web_search` | 联网搜索法规和案例 | 需要查询最新法规或地方法规时 |
| `search_document` | 在合同内部语义搜索 | 查找与当前条款相关的其他条款 |
| `search_knowledge` | 在本地法律知识库中检索 | 查询法规、案例、范本、风险模式 |
| `read_section` | 读取指定章节或条款全文 | 需要查看完整上下文时 |
| `output_finding` | 输出风险发现 | Agent 确认发现风险后 |

#### 6.4.2 专用工具

| 工具名 | 功能 | 使用场景 |
|--------|------|---------|
| `check_cross_reference` | 检查条款间引用一致性 | 例如"按本合同第 8 条执行"是否指向正确 |
| `extract_obligations` | 提取甲乙双方权利义务 | 分析权利义务是否对等 |
| `validate_calculation` | 验证金额、日期计算 | 例如经济补偿金计算是否正确 |
| `compare_with_template` | 与标准劳动合同范本对比 | 检查缺失条款 |
| `query_knowledge_graph` | 在 Neo4j 图库中做关系查询 | 查找法规-案例-风险模式的关联 |

### 6.5 记忆层详细设计

#### 6.5.1 为什么需要记忆层

Multi-Agent 架构里，每个 Agent 只负责一个审查维度。如果它们彼此孤立，就会出现"只见树木不见森林"的问题：RiskReviewAgent 发现了试用期过长，却不知道合同期限只有 2 年；MissingClauseAgent 发现缺少社保条款，却不知道 TermExtractionAgent 已经提取到"自愿放弃社保"的违法约定。记忆层就是解决这个问题的核心机制。

通俗地说，记忆层相当于一次审查会议的"公共白板"：所有 Agent 都可以把自己看到、想到、查到的信息写上去，也可以随时读取别人写上去的信息。Coordinator 则站在白板前做汇总、去重、关联和最终判断。

记忆层承担四项核心职责：

- **共享发现**：让多个 Agent 看到彼此的结果，避免重复劳动和矛盾结论；
- **保持上下文**：把单次审查中产生的条款、风险、法条、推理路径结构化保存，供后续阶段使用；
- **支撑组合推理**：把分散在不同条款里的信息关联起来，发现跨条款风险；
- **服务后续交互**：审查结束后，ChatAgent、人工复核、报告生成都能基于记忆层快速理解审查全过程。

#### 6.5.2 记忆层的三层模型

记忆层不是一个单独的物理数据库，而是由三套存储共同构成的逻辑层：

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：短期工作记忆（Working Memory）                      │
│  单个 Agent / 单次 ReAct 循环内的上下文                       │
│  载体：LLM 上下文窗口 + 当前 Agent 的本地状态                 │
│  生命周期：一次 Thought-Action-Observation 循环               │
├─────────────────────────────────────────────────────────────┤
│  第二层：会话级记忆（Session Memory）                        │
│  单次审查会话内的共享记忆                                     │
│  载体：SessionGraph + AgentBus                                │
│  生命周期：一次 review_session（从 Route 到 Triage）          │
├─────────────────────────────────────────────────────────────┤
│  第三层：长期组织记忆（Organizational Memory）               │
│  跨会话、跨用户沉淀的法律知识和审查经验                       │
│  载体：Qdrant + Neo4j + PostgreSQL + Dynamic Agent 配置       │
│  生命周期：持续积累，经 Knowledge Curator 整理后入库           │
└─────────────────────────────────────────────────────────────┘
```

**短期工作记忆**负责让单个 Agent"边查边想"。例如 RiskReviewAgent 在审查试用期条款时，会先把"试用期 6 个月"写进当前上下文，然后调用 `search_knowledge` 查法规，再把观察结果写回上下文，最后得出结论。它的生命周期很短，一次 ReAct turn 结束就被下一个 turn 覆盖。

**会话级记忆**负责让多个 Agent 协作。所有 Agent 都把关键发现写入 SessionGraph，并通过 AgentBus 广播高风险事件。Coordinator 在 Merge+Link、LegalVerify、Debate 等阶段都依赖会话级记忆做全局推理。

**长期组织记忆**负责让系统"越用越准"。审查中查过的法规、案例、风险模式，经 Knowledge Curator 整理后写入 Qdrant、Neo4j 和 PostgreSQL。下次遇到类似条款时，Agent 可以直接命中本地知识库，减少联网搜索和模型幻觉。

#### 6.5.3 SessionGraph 数据模型

SessionGraph 是会话级记忆的物理载体，采用**属性图模型**实现。每个审查会话对应一张图，节点代表审查过程中识别出的实体，边代表实体之间的关系。

**节点类型**

| 节点类型 | 含义 | 关键属性 |
|---------|------|---------|
| `Session` | 会话根节点 | `session_id`、`contract_id`、`status`、`started_at`、`completed_at` |
| `Clause` | 合同条款/Chunk | `chunk_id`、`text`、`section_path`、`page`、`bbox`、`risk_level` |
| `Risk` | 风险发现 | `risk_type`、`level`、`confidence`、`reason`、`status` |
| `Law` | 法律依据 | `law_name`、`article_number`、`article_text`、`source`、`effective_date` |
| `Case` | 典型案例 | `case_title`、`summary`、`court`、`verdict`、`reference_url` |
| `Party` | 合同主体 | `party_type`（甲方/乙方）、`name`、`role` |
| `Suggestion` | 修改建议 | `original_text`、`revised_text`、`rationale` |
| `Evidence` | 支持证据 | `evidence_type`、`content`、`source_chunk_id`、`verified` |
| `AgentState` | Agent 执行状态 | `agent_name`、`chunk_id`、`status`、`turn_count`、`logs` |

**边类型**

| 边类型 | 起点 | 终点 | 含义 |
|--------|------|------|------|
| `HAS_CLAUSE` | `Session` | `Clause` | 会话包含某条款 |
| `HAS_RISK` | `Clause` | `Risk` | 某条款存在某风险 |
| `BASED_ON` | `Risk` | `Law` | 风险依据某法条 |
| `SUPPORTED_BY` | `Risk` | `Evidence` | 风险被某证据支持 |
| `SUGGESTS` | `Risk` | `Suggestion` | 风险对应修改建议 |
| `INVOLVES` | `Clause` | `Party` | 条款涉及某主体 |
| `RELATES_TO` | `Clause` | `Clause` | 条款之间相互关联 |
| `CONTRADICTS` | `Clause` | `Clause` | 条款之间相互冲突 |
| `DEPENDS_ON` | `Risk` | `Risk` | 风险之间存在依赖 |
| `PRODUCED_BY` | `Risk` | `AgentState` | 风险由某 Agent 产生 |

**通俗解释**：可以把 SessionGraph 理解为一张"审查思维导图"。最中间是这次审查会话，向外辐射出合同条款；每个条款上可能挂着风险；每个风险上挂着法律依据、证据、修改建议；条款之间还可以画箭头表示"这两条要一起看"。

#### 6.5.4 SessionGraph 生命周期

SessionGraph 在一次审查会话中经历六个阶段：

1. **初始化（Init）**：Coordinator 创建 `Session` 根节点，写入合同元数据、Section 树引用、全局审查策略。
2. **填充（Populate）**：文档解析引擎把 Chunk 列表写入为 `Clause` 节点，建立 `Session → Clause` 边；TermExtractionAgent 提取主体信息，写入 `Party` 节点。
3. **协作写入（Collaborate）**：各 Agent 在 ReAct 循环中把 `Risk`、`Law`、`Evidence`、`Suggestion` 等节点写入，并建立相应边。
4. **合并关联（Merge+Link）**：Coordinator 扫描全图，去重、建立 `RELATES_TO` / `CONTRADICTS` 边、调整风险等级。
5. **验证固化（Verify & Triage）**：LegalVerifyAgent 验证法条，DebateAgent 辩论高风险项，HumanReviewAgent 标记待复核项，最终所有节点状态稳定。
6. **持久化与回放（Persist & Replay）**：SessionGraph 序列化为 JSON 存入 `review_sessions.graph_data`；ChatAgent 和人工复核时可以重新加载这张图。

#### 6.5.5 AgentBus 实时同步机制

SessionGraph 是被动的图存储，AgentBus 是主动的消息总线。Agent 在审查过程中通过 AgentBus 发布事件，其他 Agent 可以订阅并实时响应。

**核心事件类型**

| 事件名 | 发布时机 | 消费方 | 作用 |
|--------|---------|--------|------|
| `agent_started` | Agent 开始审查某个 Chunk | Coordinator、前端 SSE | 更新进度 |
| `agent_completed` | Agent 完成某个 Chunk | Coordinator | 触发下一阶段判断 |
| `finding_added` | Agent 写入新的 Risk | 其他 Agent、Coordinator、前端 | 实时展示风险 |
| `risk_escalated` | 风险等级被动态上调 | Coordinator、HumanReviewAgent | 触发深度审查 |
| `evidence_found` | 找到关键证据 | 相关 Risk 节点 | 增强风险置信度 |
| `contradiction_detected` | 发现条款冲突 | DebateAgent、Coordinator | 触发辩论 |
| `phase_changed` | Coordinator 阶段切换 | 前端 SSE | 更新进度条 |

**设计原则**：AgentBus 不替代 SessionGraph，而是它的"实时通知层"。重要信息必须落图，实时通知只用于加速协作和前端展示。

#### 6.5.6 Agent 读写记忆的时机

**写入时机**

- Agent 开始审查某个 Chunk 时，把该 Chunk 作为 `Clause` 节点写入（如果不存在）；
- Agent 发现风险时，把 `Risk` 节点写入，并建立 `Clause → HAS_RISK → Risk` 边；
- Agent 找到法律依据时，把 `Law` 节点写入，并建立 `Risk → BASED_ON → Law` 边；
- Agent 找到支持证据时，把 `Evidence` 节点写入，并建立 `Risk → SUPPORTED_BY → Evidence` 边；
- Agent 生成修改建议时，把 `Suggestion` 节点写入，并建立 `Risk → SUGGESTS → Suggestion` 边；
- Agent 发现条款间关联时，建立 `Clause → RELATES_TO → Clause` 边；
- Agent 发现条款冲突时，建立 `Clause → CONTRADICTS → Clause` 边；
- Agent 提取主体信息时，把 `Party` 节点写入，并建立 `Clause → INVOLVES → Party` 边。

**读取时机**

- 审查前先查看该 Chunk 是否已被其他 Agent 审查过，避免重复工作；
- 审查中查看是否有其他 Agent 已经发现相关风险，避免矛盾结论；
- 调用 `search_document` 后，把结果与 SessionGraph 中已有 Clause 做关联；
- Merge+Link 阶段查询跨条款组合风险；
- LegalVerify 阶段读取 `Risk → Law` 边，验证法条准确性；
- Debate 阶段读取 `Risk` 及其关联证据，准备正反论点；
- ChatAgent 回答用户问题时查询相关 Clause、Risk、Law 节点。

#### 6.5.7 跨 Agent 协作与组合风险发现

记忆层的最大价值在于发现"单个 Agent 看不出来的风险"。典型场景包括：

**场景一：试用期与合同期限组合**

- 条款 A：合同期限为 2 年（TermExtractionAgent 提取）；
- 条款 B：试用期为 6 个月（RiskReviewAgent 发现异常）。

单独看条款 B，Agent 只知道试用期是 6 个月；单独看条款 A，Agent 只知道合同期限是 2 年。但当两个 `Clause` 节点都在 SessionGraph 中，Coordinator 的 Merge+Link 阶段可以建立 `RELATES_TO` 边，并生成新的组合风险：

> 2 年期限的劳动合同，试用期最长只能约定 2 个月，本合同约定 6 个月，构成违法。

**场景二：自愿放弃社保 + 工资拆分**

- 条款 A：合同约定"乙方自愿放弃社保，甲方将社保费用折算为工资发放"（RiskReviewAgent 标记为高风险）；
- 条款 B：工资结构显示基本工资低于当地最低标准，其余为补贴（BalanceAgent 标记为不公平）。

两个风险单独看都很严重，组合起来则更明确：用人单位通过工资拆分规避社保缴费基数。SessionGraph 中的 `Risk → DEPENDS_ON → Risk` 边和 `Clause → CONTRADICTS → Clause` 边可以表达这种复杂关系。

**场景三：竞业限制范围与补偿标准**

- 条款 A：竞业限制范围覆盖全国同行业（RiskReviewAgent 标记）；
- 条款 B：竞业限制补偿金低于法定标准（BalanceAgent 标记）。

两个条款分别合法或违法，但组合后构成"过度限制劳动者就业权"。记忆层让不同 Agent 的发现产生关联。

#### 6.5.8 ChatAgent 对记忆层的利用

ChatAgent 不是每次从头读完整份合同，而是基于记忆层做高效回答。它的工作流如下：

1. **理解问题**：识别用户问题的意图和涉及的实体；
2. **定位节点**：在 SessionGraph 中查找相关 `Clause`、`Risk`、`Law` 节点；
3. **读取上下文**：通过边遍历获取关联风险、法条、修改建议；
4. **补充搜索**：如果问题超出已发现内容，再调用 `search_document` 或 `search_knowledge`；
5. **生成回答**：引用具体条款和风险，给出有依据的回答。

例如用户问"试用期这条有问题吗"，ChatAgent 可以直接读取 SessionGraph 中该 Clause 节点的 `HAS_RISK` 边，找到对应 Risk，再读取 `BASED_ON` 边找到法律依据，无需重新审查。

#### 6.5.9 持久化、版本管理与安全隔离

**持久化策略**

- 审查进行中，SessionGraph 驻留在内存，每隔 5 个事件异步写入 Redis 做故障恢复；
- 审查完成后，SessionGraph 序列化为 JSON 存入 `review_sessions.graph_data`；
- 关键节点（如 `Risk`、`Law`）同时写入 `findings` 和 `knowledge_articles` 表，便于单独查询和统计。

**版本管理**

- 每次 Merge+Link、LegalVerify、Debate 后生成一个 SessionGraph 快照；
- 快照编号递增，便于追溯风险结论的变化过程；
- 人工复核修改后，生成最终快照并标记为 `final`。

**安全隔离**

- SessionGraph 按 `user_id` 和 `contract_id` 做命名空间隔离；
- Agent 只能读写属于当前会话的图；
- 涉及个人身份信息（PII）的 `Party` 节点在落库时做脱敏处理；
- 长期组织记忆（法律知识库）不包含任何用户合同原文，只包含经抽象后的风险模式、法规、案例。

### 6.6 内置 Agent 说明

本项目当前共实现 **14 个内置 Agent**（另加 1 个抽象基类 `BaseAgent`），覆盖劳动合同、租赁合同、借款合同、股权转让、技术服务等多类型合同的审查维度。

#### 6.6.1 TermExtractionAgent（条款提取 Agent）

**职责**：从合同中提取关键商务条款，为后续审查提供结构化输入。

**提取字段**：

- 甲方（用人单位）名称
- 乙方（劳动者）姓名
- 合同期限（起止日期）
- 试用期（时长）
- 工作地点
- 工作岗位
- 工资标准
- 工作时间制度
- 社会保险约定
- 竞业限制约定
- 违约金约定
- 保密义务约定
- 解除条件约定

**输出**：结构化的条款信息，写入 SessionGraph 的 Clause 节点 metadata 中。

#### 6.6.2 LegalResearchAgent（法律研究 Agent）

**职责**：在 Execute 阶段之前动态推断合同适用法律领域，检索法条并生成审查要点，为后续 Agent 提供法律依据和审查清单。

**工作方式**：

1. 拼接合同文本，调用一次 LLM 同时推断**法律领域**（如劳动、租赁、借款）和**风险信号**；
2. 对每个推断出的法律领域依次执行：
   - 本地 Qdrant/关键词检索；
   - Tavily 精准联网检索（优先命中具体法条）；
   - 泛化 web search 兜底（仅在本地+精准检索无结果且该领域风险信号强时触发）；
3. 通过类级缓存 `_review_point_cache` 和 `_web_search_cache` 避免重复检索；
4. 每个合同最多触发 3 次泛化 web search，控制 API 成本。

**输出**：`discovered_laws`、`review_checklist`、`risk_signals`，写入 `context` 供后续 Agent 使用。

#### 6.6.3 RiskReviewAgent（风险审查 Agent）

**职责**：识别合同中的不公平、违法或高风险条款。当前实现采用"红线扫描 + Critic 校验 + LLM 审查"三层结构，兼顾召回与精确率。

**审查流程**：

1. **原则驱动红线扫描**：调用 `PrincipleBasedDetector` 基于 8 条通用法律原则做快速检查（数值型红线）和语义推断，先召回明确违法/高风险条款；
2. **Critic 二次校验**：对非确定性风险（尤其是 LLM 输出）调用 `CriticAgent` 的 `RuleCritic`（15 条法律常识规则）过滤常见误报；
3. **逐条审查 + 整体性审查**：先逐条审查每个 Chunk；若逐条审查产生任何 `high`/`medium` finding，或存在 surviving 的确定性红线，再触发整体性审查，避免在明显合法的合同上浪费一次全文 LLM 调用。

**审查维度**：

- 试用期是否超过法定上限
- 是否约定劳动者承担违约金（除服务期和竞业限制外）
- 竞业限制范围、期限、补偿是否合理
- 工作地点约定是否过于宽泛
- 工资是否低于当地最低工资标准
- 是否排除劳动者法定权利
- 是否约定"自愿放弃社保"等违法条款
- 解除条款是否过于偏向用人单位
- 加班工资计算是否合规

**输出**：Risk 节点，包含风险类型、等级、原因、修改建议。

#### 6.6.3 MissingClauseAgent（缺失条款检查 Agent）

**职责**：检查劳动合同是否缺少法律要求的必要条款。

**检查清单**：

- 用人单位基本信息
- 劳动者基本信息
- 劳动合同期限
- 工作内容和工作地点
- 工作时间和休息休假
- 劳动报酬
- 社会保险
- 劳动保护、劳动条件和职业危害防护
- 法律规定的其他事项

**输出**：缺失项清单，每条缺失项包含法律依据和建议补充内容。

#### 6.6.4 BalanceAgent（权利义务平衡 Agent）

**职责**：分析合同中甲乙双方权利义务是否对等。

**审查重点**：

- 甲方解除权是否过于宽泛
- 乙方辞职是否设置不合理障碍
- 违约责任是否只约束乙方
- 保密义务和竞业限制是否对等补偿
- 培训服务期约定是否合理

#### 6.6.5 CrossReferenceAgent（交叉引用检查 Agent）

**职责**：检查合同中"参见第 X 条"这类引用是否准确、一致。

例如：合同某条款写"按本合同第十条执行"，但实际合同只有八条，则标记为引用错误。

#### 6.6.6 LegalBasisAgent（法律依据 Agent）

**职责**：为已发现的风险找到准确的法律依据。

**工作方式**：

- 读取 RiskReviewAgent 和 MissingClauseAgent 输出的风险；
- 通过 `search_knowledge` 搜索相关法律条文和司法解释；
- 把法条内容、条款编号、原文摘要写入 SessionGraph；
- 建立 Risk → Law 边。

**输出**：Law 节点和 Risk → Law 边。

#### 6.6.8 SuggestionAgent（修改建议 Agent）

**职责**：为每个风险生成具体、可执行的修改建议。

**工作方式**：

- 读取 Risk 节点和关联的 Law 节点；
- 根据法律要求重写风险条款；
- 输出"原文"和"建议修改版本"的对比。

**输出**：Suggestion 节点或写入 Risk 节点的 suggestion 字段。

#### 6.6.8 IndustryComplianceAgent（行业合规 Agent）

**职责**：针对特定行业的劳动合同进行合规检查。

例如：

- 建筑行业：工伤保险、安全生产培训；
- 互联网行业：加班费、竞业限制、知识产权归属；
- 医药行业：执业资格、保密协议。

#### 6.6.9 LegalVerifyAgent（法条验证 Agent）

**职责**：验证 Agent 引用的法条是否真实、准确。

**工作方式**：

- 读取所有 Risk → Law 边；
- 在 Qdrant 和 Neo4j 中核对法条内容；
- 对无法验证或引用错误的法条进行标记；
- 必要时调用 `web_search` 二次确认。

#### 6.6.10 DebateAgent（正反辩论 Agent）

**职责**：对高风险或置信度低的发现进行正反辩论，降低误判。

**工作方式**：

- 正方 Agent：论证这确实是风险；
- 反方 Agent：论证这可能不是风险，或存在例外；
- Coordinator 根据辩论结果做最终裁决。

#### 6.6.11 BlindSpotAgent（盲区扫描 Agent）

**职责**：在主流程结束后扫描本次审查未覆盖的盲区。

**工作方式**：

- 检查是否有合同条款没有被任何 Agent 审查；
- 检查是否有新的风险模式未被现有 Agent 覆盖；
- 如果发现通用性盲区，建议生成新的 Dynamic Agent；
- 把建议写入 `dynamic_agents.json` 供后续审查使用。

#### 6.6.13 HumanReviewAgent（人工复核 Agent）

**职责**：把低置信度、高风险、组合风险、Agent 冲突项推送给人工专家复核。

**触发条件**：

- 风险置信度低于 0.7；
- 跨条款组合风险；
- 涉及"项目特点和实际需要"的复杂判断；
- 两个 Agent 结论冲突且 Debate 未能解决；
- LegalVerifyAgent 无法验证法条。

**输出**：人工复核任务，进入管理后台的复核工作台。

#### 6.6.14 ChatAgent（对话 Agent）

**职责**：基于 SessionGraph 和合同原文回答用户追问，支持同步对话和流式对话。

**工作方式**：

- 接收用户问题、选中的条款文本和当前 SessionGraph；
- 在图中定位相关 `Clause`、`Risk`、`Law` 节点，通过边遍历获取上下文；
- 必要时调用 `search_document` 或 `search_knowledge` 补充检索；
- 给出带引用来源的回答，可引用具体条款和风险结论。

**输出**：回答文本及引用列表。

#### 6.6.15 CriticAgent（批判校验 Agent）

**职责**：对候选风险做二次校验，过滤常见误报，提升审查精确率。当前主要由 `RiskReviewAgent` 在审查流程中内部调用。

**两层校验**：

1. **RuleCritic**：15 条基于法律常识的规则，覆盖否定语境、试用期比例、付款结构、违约金与损失并用、利率与罚息相加、择一主张、押金性质、质量标准等常见误报模式；
2. **LLM Critic**：当 RuleCritic 返回 `uncertain` 时，由轻量 LLM 判断候选风险是否成立。

**输出**：校验结论（`accept` / `reject` / `uncertain`）及理由。

### 6.7 风险分级

为了控制审查成本和深度，每个 Chunk 在路由阶段会被分为三个风险等级。项目统一使用 `high` / `medium` / `low` 作为标准等级，分别对应硬违规、风险、建议：

| 等级 | 含义 | 对应内部类别 | 审查深度 |
|------|------|-------------|---------|
| **high（高风险）** | 明确违法或严重不公平 | hard_violation | 深度审查 + Debate |
| **medium（中风险）** | 存在一定风险信号，需要确认 | risk | 标准审查 |
| **low（低风险）** | 格式性、通用性条款，基本无风险 | suggestion | 快速通过 |

#### 6.7.1 分级判断方法

风险分级采用两阶段方法：

1. **关键词初筛**：通过关键词匹配，快速识别高风险信号。例如"自愿放弃社保""违约金""竞业限制""砍头息"等；
2. **向量相似度确认（预留）**：用 BGE-M3 计算 Chunk 与已知风险模板的相似度，辅助确认风险等级。

#### 6.7.2 动态升降级

Agent 在审查过程中可以根据新证据动态调整等级：

- 如果 `medium` 条款找到明确违法证据，升级为 `high`；
- 如果 `high` 条款经 Debate 或 Critic 确认是误报，降级为 `medium`/`low` 或直接撤销。

## 七、法律知识库与 Knowledge Curator

### 7.1 法律知识库双层架构

Agent 调用 `search_knowledge` 时，采用"本地优先、联网兜底"的双层架构：

```
Agent 调用 search_knowledge("试用期 6个月 合法性", category="法规")
    │
    ├── 第1层：本地知识库（优先）
    │   ├── Qdrant 向量语义匹配 → Top-K 法规/案例
    │   ├── Neo4j 图遍历 → 法规→条款→案例 完整关系链
    │   └── PostgreSQL 元数据精确匹配
    │
    └── 第2层：大模型联网搜索（兜底）
        ├── DashScope 联网搜索
        └── Tavily / SearXNG 备选
```

### 7.2 Knowledge Curator

Knowledge Curator 是系统的"知识策展人"，负责把每次审查中产生的新的法规、案例、风险模式整理入库，实现系统自我进化。

**工作流程**：

1. **素材收集**：每次审查结束后，收集 Agent 搜索过但未命中本地库的法条、案例、URL；
2. **去重清洗**：CuratorDedupAgent 判断新材料是否与已有知识重复；
3. **实体抽取**：CuratorGraphAgent 从新材料中抽取 Law、Article、Case、RiskPattern 等实体；
4. **向量化**：CuratorEmbedAgent 将新材料生成向量，写入 Qdrant；
5. **建图**：CuratorGraphAgent 在 Neo4j 中建立实体关系；
6. **时效性检查**：CuratorFreshAgent 检查法规和案例是否仍然有效；
7. **人工确认**：关键材料进入管理后台待审核表，管理员确认后正式生效。

## 八、数据流说明

### 8.1 上传合同到开始审查

1. 用户在前端选择文件，调用 `POST /api/v1/contracts`；
2. FastAPI 接收文件，校验格式和大小；
3. 文件写入对象存储（本地目录或云存储）；
4. 在 `contracts` 表中创建记录，状态为 `uploaded`；
5. 调用 Celery 任务 `parse_contract_task`；
6. Celery Worker 执行文档解析，生成 RawDocument、Section 树、Chunk 列表；
7. Chunk 向量写入 Qdrant；
8. 解析完成后，`contracts` 状态更新为 `parsed`；
9. 用户点击"开始审查"，调用 `POST /api/v1/contracts/{id}/review`；
10. 启动 Celery 任务 `review_contract_task`；
11. Coordinator 创建 SessionGraph，启动 Agent 审查。

### 8.2 审查过程中的实时推送

1. Coordinator 每完成一个阶段，通过 AgentBus 发布 `phase_changed` 事件；
2. 每个 Agent 完成一个 Chunk 审查，发布 `agent_progress` 事件；
3. Agent 输出风险时，发布 `finding_added` 事件；
4. FastAPI 的 SSE 接口把这些事件推送给前端；
5. 前端更新进度条和风险卡片列表。

### 8.3 审查完成后的数据持久化

1. Coordinator 完成 Triage，生成最终 `findings` 列表；
2. SessionGraph 序列化为 JSON；
3. 写入 `review_sessions` 表的 `graph_data` 和 `findings` 字段；
4. 高风险/低置信度项进入 `human_reviews` 表；
5. `contracts` 状态更新为 `completed`；
6. 前端调用 `GET /api/v1/review/{id}/result` 获取完整结果。

### 8.4 ChatAgent 追问

1. 用户在 PDF 上划词，输入问题；
2. 前端调用 `POST /api/v1/contracts/{id}/chat` 或流式接口；
3. ChatAgent 读取 SessionGraph 和合同原文；
4. ChatAgent 在 ReAct 循环中调用 `search_document`、`search_knowledge` 或 `web_search`；
5. 返回回答，并引用相关法律和合同条款。

### 8.5 Knowledge Curator 运行

1. 系统定期（如每周）扫描近期审查会话；
2. 收集被标记为 `_curation_mark=true` 的搜索素材；
3. Curator 各子 Agent 执行去重、抽取、向量化、建图、时效性检查；
4. 新材料进入管理后台待审核表；
5. 管理员审核通过后写入 Qdrant 和 Neo4j；
6. 下次审查同一问题时，Agent 可以直接命中本地知识库。

## 十、分工安排

### 10.1 总体分工

本项目采用前后端与 Agent 分离的开发模式：

| 角色 | 负责人 | 主要职责 |
|------|--------|---------|
| Agent 开发 | 用户 | Agent Prompt 设计、ReAct 循环、工具实现、SessionGraph、Coordinator、审查准确率优化 |
| 后端开发 | 助手 | FastAPI 服务、数据库、Celery 任务、文档解析、报告生成、API 接口、Qdrant/Neo4j 集成 |
| 前端开发 | 助手 | Vue3 页面、PDF 展示、风险卡片、SSE 实时进度、ChatAgent 交互、管理后台 |

### 10.2 Agent 开发边界

Agent 开发人员主要负责：

- 设计每个 Agent 的 System Prompt；
- 实现 ReAct 循环引擎；
- 实现 Agent 工具（`web_search`、`search_document`、`search_knowledge`、`read_section`、`output_finding` 等）；
- 实现 Coordinator 的八阶段管线（含 LegalResearch 阶段）；
- 实现 SessionGraph 的构建、查询、序列化；
- 实现 AgentBus 实时消息总线；
- 实现风险分级和动态升降级逻辑；
- 实现 ChatAgent；
- 调优 Agent 输出质量和准确率。

Agent 模块对外暴露清晰的接口，后端通过调用这些接口启动审查任务。

### 10.3 后端开发边界

后端开发人员主要负责：

- FastAPI 项目脚手架搭建；
- 用户认证、合同管理、审查任务管理 API；
- PostgreSQL、Redis、Qdrant、Neo4j 的接入和配置；
- Celery 任务队列配置；
- 文档解析引擎（调用 python-docx、PyMuPDF、PaddleOCR）；
- 向量索引构建（调用 BGE-M3，写入 Qdrant）；
- 法律知识库数据导入 PostgreSQL、Qdrant、Neo4j；
- 审查任务调用 Agent 模块并接收结果；
- SSE 实时进度推送；
- 报告生成与导出；
- ChatAgent 接口封装；
- 支付订阅接口；
- 管理后台接口。

### 10.4 前端开发边界

前端开发人员主要负责：

- Vue3 项目搭建；
- 登录注册、合同列表、上传页面；
- 审查报告页面（两栏布局：PDF + 风险卡片）；
- pdf.js 集成与原文高亮；
- SSE 进度条和 Agent 状态展示；
- 风险卡片 L1 / L2 / L3 信息层级展示；
- 划词提问和 ChatAgent 对话界面；
- 管理后台页面；
- 微信小程序（可选）。

### 10.5 协作接口

Agent 模块与后端之间的核心接口约定如下：

| 接口 | 输入 | 输出 |
|------|------|------|
| `run_review(contract_id, chunks, section_tree, vector_index)` | 合同 ID、Chunk 列表、Section 树、Qdrant collection 名称 | 风险发现列表、SessionGraph JSON、人工复核项列表 |
| `chat_with_contract(contract_id, question, selected_text, session_graph)` | 问题、选中文本、SessionGraph | 回答文本、引用来源 |
| `curate_knowledge(review_session_ids)` | 近期审查会话 ID 列表 | 新入库/待审核的知识条目列表 |

Agent 模块内部自行管理 ReAct 循环、工具调用、SessionGraph 状态、法律知识库查询。后端只需提供输入数据并消费输出结果。

## 十一、安全与合规

### 11.1 数据安全

- 用户上传的合同文件加密存储；
- 数据库敏感字段加密；
- API 通信使用 HTTPS；
- 用户数据隔离，防止越权访问。

### 11.2 法律合规

- 在产品界面明确标注"AI 审查结果仅供参考，不构成法律意见"；
- 高风险和低置信度项必须转人工复核；
- 保留完整的审查日志，支持审计追溯；
- 符合《个人信息保护法》对用户数据的处理要求。

### 11.3 模型安全

- 对 LLM 输出进行 Pydantic 结构化校验；
- LegalVerifyAgent 验证所有法条引用；
- DebateAgent 对高风险项进行交叉验证；
- 限制 Agent 的最大 ReAct 轮次，防止无限循环和 token 过度消耗。

### 12.1 术语表

| 术语 | 说明 |
|------|------|
| Chunk | 条款级语义片段，是 Agent 审查的基本单位 |
| ReAct | Reasoning + Acting，让模型通过思考-行动-观察循环完成任务 |
| 记忆层 | 由 SessionGraph、AgentBus 和长期法律知识库共同构成的跨层共享记忆与知识支撑体系 |
| 短期工作记忆 | 单个 Agent / 单次 ReAct 循环内的上下文，载体为 LLM 上下文窗口 |
| 会话级记忆 | 单次审查会话内的共享记忆，载体为 SessionGraph + AgentBus |
| 长期组织记忆 | 跨会话沉淀的法律知识与审查经验，载体为 Qdrant + Neo4j + PostgreSQL |
| SessionGraph | 单次审查会话的共享记忆图，记录条款、风险、法条等实体及它们之间的关系 |
| Coordinator | AI 审查引擎的调度中心，控制审查流程 |
| AgentBus | Agent 之间的实时消息总线 |
| BBox | 文本在 PDF 页面上的坐标矩形，用于原文高亮 |
| SSE | Server-Sent Events，服务器向客户端推送实时事件 |
| Knowledge Curator | 知识策展人，自动整理和沉淀审查中产生的新知识 |
| HumanReviewAgent | 人工复核 Agent，把低置信度/高风险项推送给人工专家 |
