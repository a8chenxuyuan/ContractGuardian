# 合同卫士：AI 智能合同审查助手

## 一、项目概述

### 1.1 项目定位

一款面向 **B 端企业和 C 端用户** 的 AI 智能合同审查助手。用户上传劳动合同、借款合同、租赁合同、股权转让协议等合同文件后，系统自动识别合同中的高风险、中风险、低风险问题，并生成一份包含法律依据、修改建议、人工复核提示的结构化审查报告。

### 1.2 核心亮点

- **基于真实法律条文库**：结合本地法律知识库、联网检索和法条缓存，拒绝 AI 编造法条
- **多 Agent 协作完成审查**：14 个专业 Agent 按 8 阶段流水线协作，覆盖法律研究、风险识别、缺失条款、交叉引用、法条验证
- **动态法律研究**：不是硬编码法律规则，而是根据合同内容实时推断法律领域并检索对应法条
- **三层过滤机制**：RedFlagDetector 原则性红线 + LLM 风险审查 + CriticAgent 二次校验，兼顾准确率与召回率
- **误报控制**：通过 15 条通用法律常识规则过滤常见误报，如"违约金与赔偿损失可并用""不得用于赌博是合法限制"
- **合法合同快速通过**：对无明显风险信号的合同减少 LLM 调用和联网搜索，审查时间从数小时压缩到数分钟
- **SSE 实时推送每个 Agent 的执行进度**：用户可实时看到当前处于哪个审查阶段、已发现多少风险
- **报告支持 PDF / Word 导出**：生成的审查报告可直接用于企业内部流转或法务复核

### 1.3 技术栈

#### 前端技术栈

`Vue 3` + `TypeScript` + `Vite` + `Element Plus` + `pdf.js` + `mammoth.js`

#### 后端技术栈

`FastAPI` + `SQLAlchemy(async)` + `Pydantic v2` + `Celery` + `Redis` + `PostgreSQL` + `Qdrant` + `BGE-M3` + `百炼 LLM` + `Tavily API`

## 二、需求分析

### 2.1 用户痛点

- **信息分散**：做合同审查需要反复查阅法条、司法解释、案例，耗时耗力
- **内容虚假**：部分 AI 工具会编造法律条文，导致审查结论不可靠甚至误导用户
- **标准不一**：不同法务人员的经验和关注点不同，审查质量存在波动
- **效率低下**：一份普通合同审查往往需要 30 分钟到数小时，复杂合同需要数天
- **缺乏依据**：普通用户看不懂风险背后的法律依据，也不知道如何修改

### 2.2 用户目标

- **中小企业**：没有专职法务，需要低成本、高效率地识别合同风险
- **企业法务**：合同量大、时间紧，需要 AI 做初筛，把精力留给复杂谈判
- **律师 / 法务团队**：用 AI 完成重复性初级审查，提升人效
- **HR / 行政人员**：经常处理劳动合同，但对劳动法具体条款不够熟悉

### 2.3 核心需求

- **真实可靠**：每个风险都必须有真实法律依据，法条可被验证
- **多类型支持**：覆盖劳动合同、借款合同、租赁合同、股权转让协议等常见合同
- **可执行**：不仅指出风险，还要给出具体修改建议，部分提供修改后文本
- **可解释**：每个风险都能追溯到具体条款原文和对应法律条文
- **实时反馈**：审查过程可见，每个 Agent 的执行进度实时展示

## 三、产品设计思路

### 3.1 整体框架：以多 Agent 协作为核心

本系统的核心设计不是传统的前后端 CRUD，而是一个围绕 **多 Agent 协作** 构建的智能流水线。前端负责收集需求（上传合同）和展示结果（审查报告），后端负责调度和持久化，真正的大脑是 **14 个专业 Agent 节点**。

```
用户前端（Vue 3）
    ↓ HTTP / SSE
后端 API（FastAPI）
    ↓ 启动后台任务
多 Agent 执行图（14 个节点，8 阶段流水线）
    ↓ 调用外部工具
百炼 LLM / BGE-M3 Embedding / Tavily 联网搜索 / Qdrant 向量库
    ↓ 写入
PostgreSQL 数据库 + Redis
```

把一次合同审查拆分成多个专业子任务，每个 Agent 只负责一件事，通过共享 **SessionGraph** 协作完成最终审查报告。这种方式比单一 Prompt 直接审查全合同更稳定、更可解释、更容易调试。

### 3.2 核心设计思想

本系统采用"先规则、后 LLM"的策略：日违约金超过 0.1%、年利率超过 12%、试用期超过法定上限等确定性问题，直接用规则判定，不需要 LLM"思考"。规则跑得快、成本低、结果稳定，LLM 只负责处理需要语义理解的复杂场景。

与传统系统为每种合同类型硬编码规则不同，本系统通过 LegalResearchAgent 动态推断法律领域并检索对应法条。这样新增合同类型时，不需要改代码，只需要更新法律知识库。

为控制误报，系统采用三层过滤：第一层是 RedFlagDetector 红线规则，第二层是 LLM 风险审查，第三层是 CriticAgent 二次校验。层层过滤后，误报率大幅降低（内部测试中，14 份合法合同实现 0 误报）。

对没有明显风险信号的合同，系统会走"快速路径"：跳过泛化联网检索、跳过整体性 LLM 审查、减少不必要的 Agent 调用。这样合法合同不会被"过度审查"，成本和时间都显著下降。

此外，每个风险都能追溯到具体条款原文、引用的法律条文、由哪个 Agent 发现、是否经过辩论、是否建议人工复核，全过程可解释。

## 四、技术实现方案（聚焦 Agent 与知识库）

### 4.1 前端与后端

- **前端**：`Vue 3` + `TypeScript` + `Vite` + `Element Plus`
  - 核心页面包括：合同列表、上传合同页、审查详情页、风险报告页、对话追问页
- **后端**：`FastAPI` + `Pydantic v2` + `SQLAlchemy 2.0(async)` + `Celery` + `PostgreSQL`
  - 主要职责是接收合同上传、启动异步审查任务、提供 SSE 实时流、持久化审查结果

### 4.2 多 Agent 协作设计

#### 4.2.1 编排式 Multi-Agent

本项目没有采用一个 Main Agent 动态调用多个 Sub Agent 的模式，而是采用 **编排式 Multi-Agent**：

- 14 个 Agent 按固定 **8 阶段流水线** 顺序执行，其中 Execute 阶段内部可并行
- 每个 Agent 有明确的输入、输出和职责边界
- 通过共享 **SessionGraph** 传递数据

原因：

1. 每个步骤的输出都可以被校验和观察
2. 调试方便：哪个 Agent 出错，日志里一目了然
3. 扩展容易：新增 Agent 只需要插入到合适的位置

#### 4.2.2 14 个 Agent 的详细职责

| Agent | 输入 | 输出 | 核心功能 |
|-------|------|------|----------|
| **RouteAgent** | 合同标题、前几句文本 | 合同类型 | 判断合同类型，决定后续审查策略 |
| **PreloadAgent** | 合同文件 | chunks、章节树 | 解析 PDF / DOCX，提取文本，拆分条款 |
| **LegalResearchAgent** | 合同 chunks、合同类型 | 法条列表、审查清单、风险信号 | 推断法律领域，检索相关法条 |
| **RiskReviewAgent** | chunks、法条、审查清单 | Risk 节点 | 逐条审查条款，识别风险 |
| **CriticAgent** | RiskReviewAgent 的候选风险 | 过滤后的风险 | 用规则和 LLM 二次校验，过滤误报 |
| **MissingClauseAgent** | 合同全文 | 缺失条款类风险 | 检查劳动合同等是否缺少必备条款 |
| **BalanceAgent** | 合同全文 | 公平性类风险 | 从全局审视双方权利义务是否对等 |
| **CrossReferenceAgent** | 所有 Clause 节点 | 跨条款冲突类风险 | 检查合同前后条款是否冲突 |
| **LegalBasisAgent** | Risk 节点 | 补充后的 Risk | 为风险补充法律依据 |
| **LegalVerifyAgent** | 带法条引用的 Risk | 验证后的 Risk | 验证法条是否真实有效 |
| **SuggestionAgent** | Risk 节点 | 带修改建议的 Risk | 为每个风险生成可执行的修改建议 |
| **IndustryComplianceAgent** | 合同全文、行业 | 行业合规类风险 | 识别特定行业的特殊合规风险 |
| **DebateAgent** | high 等级 Risk | 辩论结论 | 对高风险进行正反辩论，减少误报 |
| **BlindSpotAgent** | 所有 Risk、Clause | 盲区类风险 | 从全局视角发现其他 Agent 遗漏的风险 |
| **HumanReviewAgent** | 所有 Risk | 人工复核项 | 判断哪些风险需要专家人工复核 |
| **ChatAgent** | 用户问题、审查结果 | 回答内容 | 基于审查结果回答用户追问 |

#### 4.2.3 Agent 之间沟通

所有 Agent 共享同一个 **SessionGraph**（一个图结构），每个 Agent 从图中读取自己需要的数据，处理完成后把结果写回图中。下一个 Agent 继续读取更新后的图。

与链式调用的区别：不是 A 的输出直接作为 B 的输入，而是 A 把结果放到公共白板上，B 从白板上取自己需要的部分。

### 4.3 Agent 的工具系统

每个 Agent 通过调用外部工具完成具体任务：

| 工具 | 功能 | 使用 Agent |
|------|------|------------|
| `search_knowledge` | 本地法律知识库检索 | LegalResearchAgent、LegalBasisAgent |
| `search_document` | 合同条款语义检索 | RiskReviewAgent、CrossReferenceAgent |
| `search_web` | Tavily 联网搜索法条 | LegalResearchAgent |
| `fetch_and_cache_article` | 抓取并缓存具体法条 | LegalResearchAgent |
| `red_flag_detect` | 红线规则扫描 | RiskReviewAgent |
| `output_finding` | 输出风险结果 | RiskReviewAgent、MissingClauseAgent 等 |

工具调用方式不是 ReAct 推理，而是 **「LLM 结构化生成 + 代码主动调用工具」**。Agent 内部用代码决定调用哪些工具，把工具结果整理后写入 SessionGraph。

### 4.4 Prompt 设计

- **Prompt 模板集中管理**：所有 Agent 的 Prompt 写在对应 Agent 类的 `system_prompt` 中
- **JSON 输出约束**：每个 Agent 要求 LLM 输出严格 JSON，方便 Pydantic 校验
- **关键约束反复强调**：例如 RiskReviewAgent 的 Prompt 里明确要求「没明显问题时应输出 level='low'，不要勉强找问题」
- **法条摘要机制**：把检索到的大段法条信息压缩成关键字段，让 Prompt 控制在合理长度
- **风险等级校验**：LLM 输出后必须校验 risk level 是否为 high / medium / low，非标准值会被拒绝

### 4.5 记忆系统设计

| 层级 | 存储 | 内容 | 使用时机 |
|------|------|------|----------|
| **短期记忆** | SessionGraph | 当前合同审查的上下文 | 单次审查内传递 |
| **中期记忆** | PostgreSQL user_preferences | 结构化用户偏好 | 每次新建审查时读取 |
| **长期记忆** | PostgreSQL 审查历史 + Qdrant | 具体审查事件、常见风险模式 | 按语义相似度召回 |

- 中期记忆是结构化键值对，直接查表全量读取写进 Prompt
- 长期记忆是非结构化文本，通过 Embedding 后存入 Qdrant，按当前查询语义召回最相关的几条

### 4.6 RAG 与知识库设计

知识库的作用不是替代 LLM 的推理能力，而是给 LLM 提供真实、准确、可引用的法律背景信息，避免它编造法条或给出错误的法律解释。

#### 4.6.1 知识库的路径

| 路径 | 目标 | 数据来源 | 使用方式 | 缓存策略 |
|------|------|----------|----------|----------|
| 法条原文检索 | 为审查提供真实法律依据 | 《民法典》《劳动合同法》等基础法律 + 司法解释 | LegalResearchAgent 按需检索 | 按 `法律名称 + 条款号` 缓存 |
| 合同条款语义检索 | 为跨条款检查、风险定位提供语义支持 | 用户上传的合同内容 | RiskReviewAgent 从 Qdrant 检索 | 按 contract_id 管理 |
| 联网法条兜底 | 本地库缺失时补充最新法条 | Tavily 搜索 + 权威法律网站 | LegalResearchAgent 泛化搜索 | 检索结果写入缓存 |

#### 4.6.2 知识库框架

```
用户查询 / Agent 需求
    ↓
Embedding 模型（BAAI/bge-m3）
    ↓
Qdrant 向量库
    ↓
语义相似度 Top-K 检索
    ↓
召回文本片段
    ↓
写入 Prompt 上下文
```

数据预处理：

- **文本分块（Chunk）**：把长法条和合同条款切分成适合 Embedding 的小段
- **Embedding**：把文本转换为 1024 维向量
- **元数据**：每个向量携带法律名称、条款号、合同 ID、来源类型等标签

### 4.7 核心能力详解

#### 4.7.1 RedFlagDetector 原则性红线检测

RedFlagDetector 是系统的"第一道防线"，专门处理那些不需要 LLM 就能判断的明显违法行为。

| 红线类型 | 示例 |
|----------|------|
| 数值型红线 | 日违约金超过 0.1%、一次性违约金超过合同标的 30%、年利率超过 12%、试用期超过法定上限 |
| 语义型红线 | "工伤概不负责""自愿放弃社保""不得主张任何赔偿"等明显违法的霸王条款 |

当规则判断为 high 风险但 LLM 判断为 low 时，系统会强制采用规则结果，并同步更新原因和建议。这是防止 LLM "过度宽容" 的关键机制。

#### 4.7.2 CriticAgent 误报过滤

CriticAgent 是 RiskReviewAgent 的"质检员"，专门过滤常见误报。

它内置 15 条通用法律常识规则，例如：
- "不得用于赌博"是合法限制，不是违法目的
- 违约金与赔偿损失在中国法下可以并用
- 前言概括用途与具体条款不一致时，通常以具体条款为准
- 双方违约金基数不同，不等于违约金条款显失公平

规则能快速判断的直接过滤；规则无法确定的，再交给 LLM Critic 做二次判断。

#### 4.7.3 LegalResearchAgent 动态法律研究

这是系统相比传统合同审查工具的最大差异点。

处理流程：
1. 读取合同摘要（≤3500 字）
2. 一次 LLM 调用同时推断：涉及哪些法律领域、有哪些风险信号
3. 按「本地库 → 精准联网 → 泛化联网」三层检索法条
4. 每个领域最多保留 1 条最相关法条
5. 用法条生成审查要点清单

关键优化：
- 本地库命中时不走联网检索
- 风险信号弱时跳过泛化联网搜索
- 高频法条直接走模板，不调用 LLM
- 已检索法条按 `法律名称 + 条款号` 缓存复用

#### 4.7.4 合法合同快速路径

对没有强风险信号的合同，系统会走"快速路径"：
- 跳过泛化联网检索
- 跳过整体性 LLM 审查
- 减少 LLM 调用次数

效果：在内部 28 份合同的批量测试中，合法合同的处理时间从约 4.2 小时优化到约 1.77 小时，降幅超过 50%。

#### 4.7.5 DebateAgent 辩论校验

对 high 等级风险，DebateAgent 会进行正反辩论：
- 正方：论证这为什么是风险
- 反方：论证这为什么不是风险
- 最终给出保留 / 降级 / 撤销结论

辩论结论会写回 Risk 节点，在 Triage 阶段生效。如果结论为"撤销"，该风险不会出现在最终报告中。

### 5.3 Token 及其他成本

| 项目 | 用量估计 | 说明 |
