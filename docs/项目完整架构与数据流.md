## 一、项目定位与目标用户

### 1.1 解决什么问题

合同审查是企业和个人高频但高成本的法律需求。传统方式依赖律师逐字阅读，存在三个痛点：

- **贵**：专业律师按小时或按份收费，批量审查成本极高；
- **慢**：一份复杂合同可能需要数小时甚至数天；
- **不一致**：不同律师的经验、关注点、输出格式差异很大。

合同卫士的目标是用 AI 把合同审查变成一项可规模化的在线服务：用户上传合同文件，系统自动识别风险、给出法律依据和修改建议，用户可实时查看进度、在线对话追问、导出报告。

### 1.2 核心能力

- **多格式解析**：支持 PDF、Word 文档，未来可扩展图片 OCR；
- **多类型合同**：覆盖劳动合同、租赁合同、借款合同、股权转让协议、技术服务合同、保密协议等；
- **多维度审查**：从条款提取、风险识别、缺失条款、权利义务平衡、法条验证、修改建议、跨条款组合风险、盲区扫描等角度综合审查；
- **可解释输出**：每条风险都附带涉及条款、风险原因、法律依据、修改建议、原文位置；
- **实时交互**：前端通过 SSE 实时接收审查进度，审查完成后可与合同进行对话式问答；
- **人工闭环**：用户可对风险结果点赞/驳回/纠错，系统记录人工复核意见用于后续优化。

### 1.3 目标用户

- **企业法务**：批量审查采购合同、劳动合同、保密协议；
- **中小企业主**：租办公室、签技术服务、借款前快速过一遍合同；
- **法律科技从业者**：作为底层审查引擎，嵌入自己的 SaaS 或律所系统。

## 二、系统总体架构

如果把合同卫士比作一家小型律师事务所，那么它的架构可以对应为：

| 系统分层 | 类比角色 | 主要职责 |
|----------|----------|----------|
| 前端（Vue3） | 客户接待大厅 | 上传文件、查看进度、阅读报告、对话、导出 |
| 后端 API（FastAPI） | 前台与行政 | 接收请求、鉴权、把任务分发给后台、返回结果 |
| 任务队列（Celery + Redis） | 任务调度员 | 把解析任务、审查任务异步交给 Worker 执行 |
| 文档解析服务 | 文件整理员 | 把 PDF/Word 拆成结构化条款 |
| AI 审查引擎（Agent 系统） | 律师团队 | 多 Agent 并行审查合同 |
| 共享记忆图（SessionGraph） | 案件卷宗 | 存放本次审查的所有中间结论 |
| 向量数据库（Qdrant） | 案例与法条检索室 | 语义检索相似条款和法律知识 |
| 关系数据库（PostgreSQL） | 档案柜 | 持久化用户、合同、审查会话、风险发现 |
| 法律知识库 + 联网搜索 | 法律图书馆 | 提供准确、可引用的法律依据 |

从技术栈看，系统采用经典的“前后端分离 + 异步任务队列 + 多 Agent AI 引擎”模式。

### 2.1 分层架构详解

#### 第一层：前端层

前端基于 Vue3 + Vite 构建，打包后由 FastAPI 托管为单页应用。前端不关心 AI 如何审查，只负责三件事：

- **收集输入**：用户上传合同、选择合同类型、填写补充信息；
- **展示进度**：通过 SSE 连接后端流式接口，实时显示当前审查阶段；
- **呈现结果**：以风险卡片、原文高亮、统计图表、对话窗口、导出按钮等形式展示审查报告。

#### 第二层：后端 API 层

后端基于 FastAPI，采用异步 IO 处理并发请求。主要职责包括：

- **用户认证与鉴权**：注册、登录、JWT Token 校验，确保用户只能访问自己的合同；
- **合同管理**：上传、列表、详情、删除合同；
- **审查会话管理**：创建审查会话、查询结果、获取风险列表、导出报告；
- **对话接口**：基于 SessionGraph 回答用户关于合同的追问；
- **反馈接口**：接收用户对风险结果的人工复核；
- **静态文件服务**：提供上传文件和生成报告的下载。

#### 第三层：异步任务层

解析合同和审查合同都是耗时操作，不能阻塞 HTTP 请求。因此系统使用 Celery 作为分布式任务队列，Redis 作为 Broker 和 Backend。

- **解析任务**：`parse_contract_task` 读取上传文件，生成结构化条款数据；
- **审查任务**：`review_contract_task` 调用 AI 审查引擎，生成风险结果。

任务执行期间，Worker 通过 Redis Pub/Sub 发布进度事件，前端 SSE 接口订阅同一频道，实现实时推送。

#### 第四层：AI 审查引擎层

这是整个系统的核心，由 Coordinator、多个专业 Agent、共享记忆图 SessionGraph、工具函数、配置规则等组成。后文会单独用完整章节详细拆解。

#### 第五层：数据与知识层

- **PostgreSQL**：持久化用户、合同、审查会话、风险发现、人工复核等结构化数据；
- **Redis**：Celery Broker、SSE 事件广播、会话状态缓存；
- **Qdrant**：向量数据库，存储合同条款向量和法律知识向量，支持语义检索；
- **Neo4j**：知识图谱数据库，用于法律概念之间的关系推理；
- **法律知识库**：本地法条数据 + Tavily 联网搜索缓存；
- **对象存储**：本地文件系统或云对象存储，保存上传合同和生成报告。

## 三、核心数据实体与关系

理解数据实体是理解数据流的前提。本系统围绕四类核心实体运转：用户、合同、审查会话、风险发现。

### 3.1 用户

用户是系统的最小使用单元。每个用户拥有一份独立的合同列表，所有操作都基于 JWT Token 进行鉴权。用户可以进行注册、登录、上传合同、启动审查、查看报告、提交反馈等操作。

### 3.2 合同

合同是用户上传的原始文件及其解析结果的总称。一份合同包含：

- **基本信息**：文件名、文件类型、页数、上传时间、当前状态；
- **文件版本**：支持版本管理，当前主要保存原始文件的存储路径；
- **解析数据**：PDF/Word 解析后的结构化数据，包括全文文本、条款 chunks、章节树、合同类型推断结果；
- **风险摘要**：最后一次审查完成后生成的高中低风险统计；
- **审查会话列表**：一份合同可以被多次审查，每次形成一个审查会话。

合同状态会随着处理流程推进而变化：

```text
uploaded（已上传） → parsing（解析中） → parsed（已解析）
                                          ↓
                                   reviewing（审查中） → completed（已完成）/ failed（失败）
```

### 3.3 审查会话

审查会话代表一次完整的 AI 审查过程。它的核心字段包括：

- **状态**：pending / running / completed / failed；
- **图数据**：SessionGraph 的序列化结果，包含所有 Clause 节点、Risk 节点、Law 节点和它们之间的关系；
- **风险列表**：本次审查输出的结构化风险发现；
- **统计信息**：高风险、中风险、低风险的数量，以及处理耗时等；
- **完成时间**：用于报告生成和审计。

### 3.4 风险发现

风险发现是系统最终呈现给用户的核心内容。每条风险发现包括：

- **风险类型**：如“试用期超长”“违法约定违约金”“借款利率超过法定上限”等；
- **风险等级**：high / medium / low；
- **置信度**：0 到 1 之间的数值，表示模型对该风险的把握程度；
- **涉及条款文本**：触发该风险的具体合同条款原文；
- **风险原因**：为什么这条条款有问题；
- **法律依据**：引用的具体法律条文；
- **修改建议**：包括修改后的条款文本或修改方向；
- **原文位置**：可选的 BBox 坐标，用于前端在 PDF 中高亮定位；
- **复核状态**：active / confirmed / dismissed，记录用户是否认可该风险。

### 3.5 实体关系总结

```text
一个用户  ──拥有──▶  多份合同
一份合同  ──包含──▶  一个原始文件 + 解析数据
一份合同  ──产生──▶  多个审查会话
一个审查会话  ──包含──▶  多个风险发现
一个风险发现  ──可被──▶  多个人工复核记录
```

## 四、端到端数据流：从用户上传到报告导出

下面按照时间顺序，详细描述一份合同在系统中经历的完整旅程。

### 4.1 第一步：用户上传合同

用户在前端点击上传按钮，选择一份 PDF 或 Word 合同。前端把文件通过 HTTP 请求发送到后端的合同上传接口。

后端收到请求后：

1. **校验文件格式**：仅支持 pdf、docx、image 类型；
2. **保存原始文件**：通过 StorageService 把文件写入本地上传目录，生成唯一文件名；
3. **创建合同记录**：在 PostgreSQL 的 `contracts` 表中插入一条记录，状态为 `uploaded`；
4. **创建文件版本记录**：在 `contract_files` 表中记录文件存储路径和大小；
5. **触发解析任务**：调用 Celery 异步任务 `parse_contract_task`，把合同 ID、文件路径、文件类型交给 Worker；
6. **返回响应**：告诉用户“上传成功，正在解析中”。

此时合同状态变为 `parsing`。

### 4.2 第二步：异步解析合同

Celery Worker 收到解析任务后，调用文档解析服务 `ContractParser`。

解析过程根据文件类型分支：

- **PDF**：使用 PyMuPDF 打开文件，逐页提取文本块和坐标，每个文本块作为一个段落候选；
- **Word**：使用 python-docx 读取每个段落；
- **图片**：预留 OCR 接口，当前未完整实现。

解析器接下来做三件事：

1. **识别条款标题**：通过正则匹配“第 X 条”“一、”“（一）”“1.”等常见标题模式，把段落聚合成条款；
2. **构建章节树**：根据“章”“节”“条”的层级关系，构建出 `section_tree`，保留合同原本的层级结构；
3. **推断合同类型**：基于标题和全文关键词，判断这是劳动合同、租赁合同、借款合同、股权转让协议还是通用合同。

解析完成后，Worker 把结果写回数据库：

- `contracts.parsed_data` 字段保存完整的结构化解析结果，包括 `chunks`、`section_tree`、`full_text`、`contract_type`、`page_count` 等；
- `contracts.status` 更新为 `parsed`。

前端可以通过轮询或 SSE 感知到解析完成。

### 4.3 第三步：用户启动审查

解析完成后，用户在前端点击“开始审查”按钮。后端创建一个新的 `ReviewSession` 记录，状态为 `pending`，然后触发 Celery 异步任务 `review_contract_task`。

如果 Redis/Celery 不可用，后端会降级为在当前进程同步执行审查任务，确保 demo 环境也能跑通。

### 4.4 第四步：异步 AI 审查

这是整个系统最复杂的一步。Celery Worker 收到审查任务后，会调用 AI 审查引擎的入口：`ReviewCoordinator`。

Coordinator 把一次审查拆成八个阶段：

```text
Route → Preload → LegalResearch → Execute → Merge+Link → LegalVerify → Debate → Triage
```

每个阶段的具体工作在“八阶段审查管线详解”章节展开。这里先概述数据如何流动：

1. Coordinator 从数据库读取 `parsed_data`，得到 `chunks` 和 `section_tree`；
2. Coordinator 创建一个新的 `SessionGraph` 实例作为本次审查的共享记忆；
3. 八阶段管线依次执行，各 Agent 把中间结果写入 SessionGraph；
4. 审查完成后，Coordinator 把 SessionGraph 中的风险发现、图数据、统计信息返回；
5. Worker 把这些结果写回数据库的 `ReviewSession` 和 `Finding` 表；
6. Worker 更新合同状态和 `risk_summary`。

审查期间，Coordinator 和 Agent 通过 `AgentBus` 向 Redis 频道发布阶段切换事件和高风险发现事件。前端 SSE 接口订阅同一频道，实时显示进度。

### 4.5 第五步：前端展示结果

审查完成后，前端可以通过以下接口获取结果：

- **审查结果接口**：返回审查会话的整体信息，包括风险列表和统计；
- **风险列表接口**：返回本次审查的所有风险发现，支持分页和筛选；
- **SSE 接口**：在审查进行中也持续推送 `phase_changed`、`finding_added`、`completed` 等事件。

前端把风险按高中低分级展示，支持：

- 展开风险卡片查看原因、法条、修改建议；
- 在 PDF 原文中高亮对应条款位置；
- 对风险进行确认/驳回/纠错反馈。

### 4.6 第六步：报告导出

用户可以点击“导出报告”，选择 PDF 或 Word 格式。后端根据 `ReviewSession` 中的风险列表和统计信息生成报告文件：

- **PDF 报告**：使用 WeasyPrint 把 HTML 渲染为 PDF，包含封面、统计摘要、风险详情；
- **Word 报告**：使用 python-docx 生成 docx 文件；
- **降级方案**：如果 WeasyPrint 未安装，则生成 HTML 文件供用户下载。

生成的报告文件保存在本地报告目录，前端通过文件下载接口获取。

### 4.7 第七步：对话与反馈

审查完成后，用户还可以：

- **对话追问**：基于当前合同内容和 SessionGraph，向 ChatAgent 提问，例如“这份合同的试用期是否合法？”ChatAgent 会定位相关条款和风险节点，给出带引用的回答；
- **提交反馈**：对某条风险标记“正确”或“有误”，并填写理由。系统把反馈写入 `HumanReview` 表，并把对应 `Finding` 的状态更新为 `confirmed` 或 `dismissed`。

这些反馈数据未来可用于：

- 优化 Prompt 和规则；
- 调整 Agent 的置信度阈值；
- 构建训练数据，持续改进模型表现。

## 五、AI 审查引擎：多 Agent 协作体系

AI 审查引擎是合同卫士的技术核心。它不是一个单一的大模型，而是一个由多个专业 Agent 组成的协作系统。

### 5.1 编排式 Multi-Agent 架构

本项目采用**编排式 Multi-Agent**，而非“主 Agent + 子 Agent”的树状结构。

**编排式的核心思想**：

- 有一个中心调度器 `ReviewCoordinator`，它只负责流程控制，不参与具体审查；
- 每个 Agent 都是独立的专业角色，只关注自己的审查维度；
- Agent 之间不直接通信，而是通过共享的 `SessionGraph` 读取和写入数据；
- 多个 Agent 可以在 Execute 阶段并行执行，提高效率。

这种架构的好处是：

- **职责清晰**：调度、通信、业务审查、数据存储各自独立；
- **易于扩展**：新增一个 Agent 只需要实现它的业务逻辑并在 Coordinator 中注册；
- **状态可追溯**：所有中间结论都保存在 SessionGraph 中，方便调试和审计；
- **并发高效**：Execute 阶段多个 Agent 同时工作，不需要串行等待。

### 5.2 Agent 的分类与职责

当前系统共有 14 个可运行的内置 Agent，加上 1 个抽象基类 `BaseAgent`。它们可以分为四类：

#### 信息提取类

- **TermExtractionAgent**：提取合同关键商务条款，如甲乙双方名称、金额、期限、付款方式等，为后续审查提供基础信息。

#### 风险审查类

- **RiskReviewAgent**：最核心的风险识别 Agent。它内部采用“红线扫描 + Critic 校验 + LLM 审查”三层结构，识别不公平、违法或高风险条款。
- **MissingClauseAgent**：检查合同是否缺少必要条款，如劳动合同缺少工作内容、工作地点、劳动报酬等。
- **BalanceAgent**：分析双方权利义务是否对等，识别明显偏向一方的条款。
- **CrossReferenceAgent**：检查前后条款引用是否一致，例如前文约定“违约金 10%”，后文又写“违约金 20%”。
- **IndustryComplianceAgent**：检查行业特殊合规要求，如技术服务合同中的知识产权、保密义务等。
- **BlindSpotAgent**：扫描容易被忽略但可能隐藏风险的角落。

#### 验证与建议类

- **LegalBasisAgent**：为已有的 Risk 节点补充法律依据。
- **LegalVerifyAgent**：核对法条引用的准确性。
- **SuggestionAgent**：为风险生成具体、可执行的修改建议。
- **LegalResearchAgent**：在 Execute 阶段之前动态推断适用法律领域，检索法条并生成审查要点，为后续 Agent 提供法律依据和审查清单。

#### 复核与交互类

- **DebateAgent**：对高风险或低置信度项进行正反辩论，降低误判。
- **HumanReviewAgent**：标记需要人工复核的项。
- **ChatAgent**：基于 SessionGraph 回答用户关于合同的追问。
- **CriticAgent**：对 RiskReviewAgent 发现的候选风险做二次校验，过滤常见误报。

### 5.3 共享记忆：SessionGraph

SessionGraph 是本次审查的“案件卷宗”。它本质上是一个有向图，节点代表审查过程中产生的各种实体，边代表实体之间的关系。

#### 节点类型

- **Clause 节点**：合同的原始条款；
- **Risk 节点**：Agent 发现的风险；
- **Law 节点**：引用的法律条文；
- **Entity 节点**：从合同中提取的实体，如甲方、乙方、金额、日期等；
- **Suggestion 节点**：修改建议。

#### 边类型

- **HAS_RISK**：条款拥有某个风险；
- **SUPPORTED_BY**：风险被某条法律支持；
- **RELATES_TO**：两个条款相关联；
- **CONTRADICTS**：两个条款互相矛盾；
- **SUGGESTS**：风险对应某条修改建议。

#### SessionGraph 的核心作用

1. **共享工作区**：所有 Agent 从同一张图读取输入、写入输出，避免各自维护独立状态；
2. **去重合并**：通过法律指纹和文本相似度，把多个 Agent 发现的同一风险合并；
3. **跨条款推理**：通过图遍历发现单条款 Agent 无法识别的组合风险；
4. **可解释性**：图的节点和边本身就是审查过程的审计线索；
5. **对话基础**：ChatAgent 基于图中的节点和边回答用户追问。

### 5.4 AgentBus：实时事件总线

AgentBus 基于 Redis Pub/Sub 实现，是 Coordinator 与前端之间的“广播喇叭”。

它发布的事件类型包括：

- **phase_changed**：审查阶段切换事件，例如“进入 LegalResearch 阶段”“进入 Execute 阶段”；
- **finding_added**：新增高风险发现事件，前端可立即展示；
- **completed**：审查完成事件；
- **error**：审查过程中发生错误的事件。

SSEManager 订阅相同的 Redis 频道，把事件以 SSE 格式推送给前端。这样即使在多 Worker 部署环境下，前端也能收到正确的进度事件。

### 5.5 工具函数：Agent 的“手”

Agent 不直接操作数据库或文件系统，而是通过统一的工具函数获取外部信息。当前系统实现了 10 个工具：

- **read_section**：读取 SessionGraph 中指定条款的文本；
- **search_document**：在合同所有 chunks 中做关键词或语义检索；
- **search_knowledge**：查询法律知识库，优先走 Qdrant 语义检索，降级时走关键词查询；
- **output_finding**：把发现的风险写入 SessionGraph；
- **check_cross_reference**：检查两个条款引用是否一致；
- **extract_obligations**：提取条款中的权利义务对；
- **validate_calculation**：校验数值计算是否正确；
- **compare_with_template**：与标准模板进行对比；
- **query_knowledge_graph**：查询 Neo4j 法律知识图谱；
- **web_search**：通过 Tavily 进行联网搜索，检索外部法律条文或案例。

工具函数的设计原则是：每个工具只做一个原子操作，Agent 通过组合多个工具完成复杂任务。

## 六、八阶段审查管线详解

`ReviewCoordinator` 把一次完整审查拆成八个有序阶段。阶段之间顺序执行，但 Execute 阶段内部的多个 Agent 可以并行。

### 6.1 Route（路由分配）

Coordinator 扫描每个合同条款的内容，按关键词识别风险信号，给每个 Chunk 分配初始风险等级（high / medium / low）和需要审查它的 Agent 列表。

例如：

- 条款里出现“试用期”“社保”“竞业限制” → 标记 high，派给 RiskReviewAgent、BalanceAgent、LegalBasisAgent；
- 条款里出现“工资”“解除”“工作地点” → 标记 medium，派给 RiskReviewAgent、BalanceAgent；
- 普通格式条款 → 标记 low，默认只过 RiskReviewAgent 和 MissingClauseAgent。

Route 阶段的作用类似医院分诊台：快速判断哪位“专家”需要看哪部分，避免所有 Agent 都全文扫描，节省计算资源。

### 6.2 Preload（预加载）

Preload 阶段为后续审查准备“病历资料”：

1. 把所有条款写成 `Clause` 节点，放进 SessionGraph；
2. 把合同条款向量化，写入 Qdrant，供后续语义检索使用；
3. 调用 TermExtractionAgent 提取合同主体信息，如甲方、乙方、金额、期限等；
4. 推断合同类型，决定后续激活哪些审查维度。

### 6.3 LegalResearch（法律研究）

在正式审查之前，系统先做一次“法律调研”，明确本次审查应该依据哪些法律、重点关注哪些问题。

`LegalResearchAgent` 的工作流程：

1. 拼接合同文本，调用一次 LLM 同时推断法律领域和风险信号；
2. 对每个推断出的法律领域依次执行检索：
   - 本地 Qdrant/关键词检索；
   - Tavily 精准联网检索，优先命中具体法条原文；
   - 泛化 web search 兜底，仅在本地和精准检索都无结果且该领域风险信号强时触发；
3. 通过类级缓存避免重复检索；
4. 每个合同最多触发 3 次泛化 web search，控制 API 成本。

输出结果是 `discovered_laws`、`review_checklist`、`risk_signals`，供后续 Agent 使用。

### 6.4 Execute（执行）

Execute 阶段是多个 Agent 并行审查的核心阶段。每个 Agent 内部是一个 ReAct 循环：观察、思考、行动、调用工具、再观察，直到完成自己的审查任务。

以 `RiskReviewAgent` 为例，它内部采用三层结构：

1. **PrincipleBasedDetector 红线扫描**：基于 8 条通用法律原则做快速检查和语义推断，召回明显违法或高风险的条款；
2. **CriticAgent 二次校验**：对非确定性风险调用 RuleCritic 的 15 条法律常识规则过滤常见误报；
3. **LLM 审查**：逐条审查每个 Chunk。如果逐条审查产生了任何 high/medium 发现，或者存在 surviving 的确定性红线，才触发整体性审查，避免在明显合法的合同上浪费一次全文 LLM 调用。

其他 Agent 也类似：从 SessionGraph 读取 Clause 节点，结合 LegalResearch 输出的法律上下文，发现各自维度的风险并写回 SessionGraph。

### 6.5 Merge+Link（合并与关联）

所有 Agent 执行完毕后，Coordinator 对 SessionGraph 进行后处理：

1. **法律指纹去重**：先用 `_legal_fingerprint` 把同一法律问题的不同表述归一化，再在组内通过 clause_text 包含关系、2-gram Jaccard 相似度、clause_ids 交集判断是否重复，合并时保留最高等级和最高置信度；
2. **建立关联**：为相关条款建立 `RELATES_TO` 边；
3. **发现冲突**：为互相矛盾的条款建立 `CONTRADICTS` 边；
4. **跨条款风险**：先根据 `cross_clause_rules.json` 中的 18 条规则发现组合风险；仅当规则已命中或图中已存在 high/medium 风险时，才调用 LLM 兜底补充，避免低风险合同上的无效 LLM 调用。

### 6.6 LegalVerify（法条验证）

LegalVerifyAgent 核对每个 Risk 节点引用的法律条文是否准确、完整、与风险类型匹配。

它的工作包括：

- 检查 `law_refs` 中的法条是否真实存在；
- 检查法条内容是否与风险描述一致；
- 补充缺失的法条引用；
- 对引用不充分的风险降级或标记为需复核。

### 6.7 Debate（正反辩论）

DebateAgent 对高风险或低置信度项进行正反论证。它会让 LLM 分别扮演“支持该风险成立”和“反对该风险成立”的两方，各自陈述理由，最后由模型综合判断。

这个阶段的目的是：

- 降低误报：让模型自己挑战自己的结论；
- 提升可解释性：输出正反两面的理由，帮助用户理解；
- 筛除低质量风险：如果反方理由充分，该风险会被降级或删除。

### 6.8 Triage（分流输出）

Triage 阶段把 SessionGraph 中的风险整理成最终输出格式：

1. 收集所有 Risk 节点；
2. 按 high / medium / low 分级统计；
3. 为每个风险补充 clause_text、reason、law_refs、suggestion、bbox 等字段；
4. 生成 `findings` 列表和 `stats` 统计；
5. 把 SessionGraph 序列化为 `graph_data`。

最终输出返回给 Celery Worker，由 Worker 写入数据库。

## 七、风险检测与质量保障机制

为了保证审查既有高召回又有低误报，系统设计了多层质量保障机制。

### 7.1 原则驱动的红线检测

`PrincipleBasedDetector` 是系统的第一层防线。它不是基于固定关键词，而是基于 8 条通用法律原则：

- 比例原则：违约金、赔偿金不应过分高于实际损失；
- 权利保留原则：不得排除一方的法定权利；
- 明确性原则：关键条款应明确具体，避免模糊表述；
- 诚实信用原则：不得通过格式条款损害对方利益；
-  statutory liability non-exemption：不得约定免除法定责任；
- 试用期/租期上限原则：试用期、租赁期限不得超过法定上限；
- 劳动者保护原则：劳动合同中不得违法约定违约金、排除社保义务等；
- 公平交易原则：双方权利义务应大致平衡。

每条原则配置了 violation 示例和 non-violation 示例。检测时，系统会：

1. 对条款做快速检查，例如判断违约金比例是否超过 30%、试用期是否超过法定上限、租赁期限是否超过 20 年；
2. 对语义模糊的条款，计算它与 violation 中心、non-violation 中心的相似度；
3. 对召回的候选原则，用轻量 LLM 做最终实例化判断。

### 7.2 Critic 二次校验

`CriticAgent` 是系统的“质检员”。它对 `RiskReviewAgent` 发现的候选风险做二次校验，过滤常见误报。

它包含两层：

- **RuleCritic**：15 条基于法律常识的规则，例如：
  - 否定语境下的违法目的误判：如“不得用于赌博”是合法限制，不是违法目的；
  - 违约金与损失并用被误判为重复：中国法下违约金和赔偿损失可以并用；
  - 利率与逾期罚息被简单相加误判为超限：正常年利率和逾期罚息适用对象不同，不能简单相加；
  - 试用期未结合合同期限：未结合合同期限就判定试用期超长；
  - 正常付款结构被误判为失衡：如借款按月付息是正常安排。
- **LLM Critic**：当 RuleCritic 无法确定时，由轻量 LLM 做最终判断。

### 7.3 条件执行策略

为了避免在明显合法的合同上浪费昂贵的 LLM 调用，系统引入了条件执行：

- **整体性审查跳过**：如果逐条审查没有产生任何 high/medium 发现，且没有 surviving 的确定性红线，跳过整体性审查；
- **跨条款 LLM 兜底跳过**：如果规则未命中任何组合风险，且图中没有已存在的 high/medium 风险，跳过 LLM 跨条款检测；
- **LegalResearch 快速路径**：当本地+精准检索已有足够结果，或整体风险信号弱时，跳过泛化 web search。

这些优化把 28 份测试合同的总处理时间从约 4.2 小时降到了约 1.77 小时。

### 7.4 法律指纹去重

不同 Agent 可能从各自角度识别出语义相同的风险。例如一份劳动合同可能同时出现：

- RiskReviewAgent：试用期超长；
- 跨条款规则：试用期超长；
- LLM 兜底：试用期与解除条款风险。

系统通过**法律指纹**先把这些风险归一化到同一法律问题，再合并为一条，保留最高等级和最高置信度。这样报告不会重复，统计也更准确。

## 八、法律知识检索体系

准确的法律依据是合同审查可信度的关键。系统采用“本地知识库 + 向量检索 + 联网搜索 + 缓存”四层知识检索体系。

### 8.1 本地法律知识库

系统内置了 24 条基础法律条文，覆盖租赁、买卖、借款、技术服务、劳动法等领域。这些法条存储在 PostgreSQL 的 `knowledge_articles` 表中，启动时可以通过 `seed_knowledge.py` 脚本导入。

### 8.2 向量检索

系统使用 BGE-M3 向量模型和 Qdrant 向量数据库：

- 启动时把法条向量化写入 Qdrant 的 `knowledge_articles` collection；
- 审查时把合同条款向量化写入 Qdrant 的 `contract_clauses` collection；
- Agent 查询法条时，优先做语义相似度检索，而不是简单的关键词匹配。

如果 Qdrant 未启动或模型未加载，系统会自动降级为关键词 LIKE 查询，保证主链路不中断。

### 8.3 联网搜索与缓存

当本地知识库无法覆盖时，`LegalResearchAgent` 会调用 Tavily 进行联网搜索，检索具体法律条文原文。

为了避免重复调用 API 和节省成本：

- 外部法条以 `law_name + article_number` 为唯一键缓存到本地；
- `LegalResearchAgent` 维护类级缓存 `_review_point_cache` 和 `_web_search_cache`；
- 每个合同最多触发 3 次泛化 web search。

### 8.4 法条验证

`LegalVerifyAgent` 会对 LLM 引用的法条做校验：

- 法条是否真实存在；
- 法条编号是否正确；
- 法条内容与风险描述是否匹配；
- 必要时通过 `web_search` 补充原文。

## 九、实时进度推送机制

合同审查是耗时操作，前端不能一直轮询。系统采用 Server-Sent Events（SSE）实现实时进度推送。

### 9.1 数据流向

```text
Coordinator/Agent ──发布事件──▶ AgentBus ──写入──▶ Redis Pub/Sub 频道
                                                          ↑
前端 SSE 接口 ──订阅──▶ SSEManager ──读取──┘
```

具体流程：

1. Coordinator 每完成一个阶段，通过 AgentBus 向 Redis 频道 `review:{session_id}:events` 发布 `phase_changed` 事件；
2. Agent 发现高风险时，发布 `finding_added` 事件；
3. 审查完成后，发布 `completed` 事件；
4. 前端调用 `/api/v1/review/{id}/stream` 接口，SSEManager 订阅同一 Redis 频道；
5. SSEManager 把 Redis 消息转换为 SSE 格式推送给前端。

### 9.2 多 Worker 一致性

SSEManager 采用单例模式，确保整个应用生命周期内只有一个 Redis 连接实例。这样即使 Celery Worker 和 FastAPI 进程运行在不同机器上，只要它们连接同一个 Redis，前端就能收到正确的进度事件。

### 9.3 优雅降级

如果 Redis 不可用，AgentBus 不会阻塞审查流程，但前端可能无法收到实时进度。这是为了优先保证审查核心功能可用。

### 10.1 前端页面结构

前端主要包含以下页面：

- **登录/注册页**：用户认证；

## 十一、安全、部署与扩展性

### 11.1 安全设计

- **认证鉴权**：基于 JWT Token，用户只能访问自己的合同和审查结果；
- **文件安全**：上传文件保存在非 Web 根目录，通过静态文件接口按权限返回；
- **敏感配置**：数据库密码、Redis 密码、LLM API Key、Tavily API Key 都通过环境变量注入，不写入代码；
- **输入校验**：所有 API 入参通过 Pydantic Schema 校验；
- **SQL 注入防护**：使用 SQLAlchemy ORM，避免手写 SQL。

### 11.2 部署架构

项目通过 `docker-compose.yml` 定义了完整的基础设施：

- **PostgreSQL**：关系数据库，持久化业务数据；
- **Redis**：Celery Broker + SSE 事件广播 + 缓存；
- **Qdrant**：向量数据库；
- **Neo4j**：知识图谱数据库。

后端和 Celery Worker 可以分别部署为多实例：

- FastAPI 服务处理 HTTP 请求；
- Celery Worker 处理解析和审查任务；
- 多个 Worker 可以并行消费任务队列，提高吞吐量。

### 11.3 扩展性设计

- **新增 Agent**：实现 Agent 类并在 Coordinator 中注册即可；
- **新增合同类型**：在合同分类器和 `cross_clause_rules.json` 中添加规则；
- **新增红线原则**：在 `legal_principles.json` 中添加原则定义；
- **新增工具**：实现工具函数并在 BaseAgent 的工具注册表中注册；
- **替换 LLM**：通过环境变量切换模型，无需改动代码；
- **替换存储**：StorageService 设计为接口一致，可替换为 MinIO、OSS、S3 等云存储。

### 11.4 生产注意事项

- 生产环境应使用 Alembic 管理数据库迁移，关闭 `AUTO_CREATE_TABLES`；
- 生产环境应配置 Nginx 反向代理、SSL 证书、日志聚合；
- Celery Worker 在 Windows 上建议使用 `-P solo` 模式，避免 prefork 问题；
- BGE-M3 模型文件较大，首次下载建议使用国内镜像或预置模型文件；
- Tavily API 调用应配置限流和监控，防止成本失控。

## 十二、总结

合同卫士是一个完整的 AI 合同审查系统，它的核心价值在于把“律师逐字审合同”变成“用户上传、系统自动、实时可看、可导出可对话”的在线服务。

从技术视角看，它的关键设计可以总结为：

1. **八阶段审查管线**：把复杂审查任务拆成可调度、可观测、可优化的阶段；
2. **编排式 Multi-Agent**：14 个专业 Agent 并行协作，各司其职；
3. **共享记忆图 SessionGraph**：所有 Agent 在同一图上工作，支持去重、跨条款推理、对话和审计；
4. **原则驱动的红线检测**：PrincipleBasedDetector 用通用法律原则覆盖明确违法场景；
5. **Critic 二次校验**：RuleCritic + LLM Critic 过滤常见误报；
6. **条件执行优化**：避免在合法合同上浪费昂贵 LLM 调用，显著提升性能；
7. **四层知识检索**：本地法条 + 向量检索 + 联网搜索 + 缓存，保证法律依据准确；
8. **端到端数据闭环**：从上传、解析、审查、展示、导出、对话到反馈，形成完整产品链路。

理解这套架构后，无论是排查问题、新增功能、优化性能，还是向他人介绍项目，都能做到心中有数。
