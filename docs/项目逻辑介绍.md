## 一、项目整体流程与内部逻辑

### 1.1 一句话概括

合同卫士是一个 **AI 驱动的合同审查系统**。用户上传一份合同后，系统自动解析合同内容，调动多个专业 AI Agent 并行审查，发现风险、引用法条、给出修改建议，最后以结构化报告的形式展示给用户。

### 1.2 整体流程图

```text
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  用户上传    │ --> │  文档解析    │ --> │  启动审查    │ --> │  Agent 审查  │
│  合同文件    │     │  文本/章节   │     │  异步任务    │     │  多角色并行  │
└─────────────┘     └─────────────┘     └─────────────┘     └──────┬──────┘
                                                                    │
                                                                    ▼
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  用户查看    │ <-- │  前端展示    │ <-- │  后端汇总    │ <-- │  结果去重    │
│  审查报告    │     │  风险/法条   │     │  生成报告    │     │  法条验证    │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
```

### 1.3 通俗解释：像医院看病

把合同审查比作去医院看病：

- **用户上传合同** = 病人挂号，提交病历（合同文件）。
- **文档解析** = 护士把病历整理成标准化表格，标出每一页、每一段、每个检查项。
- **启动审查** = 医院把病历送进会诊系统，安排多位专家同时看。
- **Agent 审查** = 不同科室专家（风险科、法律科、合规科）各自出具诊断意见。
- **结果去重/法条验证** = 主任医师把各位专家意见汇总，去掉重复、核对依据、确认严重程度。
- **生成报告/前端展示** = 医院把最终诊断报告交给病人，标注哪里有问题、应该怎么治。

### 1.4 内部核心流程

后端收到合同后，会经历 **八阶段审查管线**：

```text
Route（路由） → Preload（预加载） → LegalResearch（法律研究） → Execute（执行）
→ Merge+Link（合并关联） → LegalVerify（法条验证） → Debate（辩论） → Triage（分流输出）
```

| 阶段 | 作用 | 通俗解释 |
|------|------|----------|
| **Route** | 扫描每个条款，按关键词分配初始风险等级（`high`/`medium`/`low`）和待审 Agent | 分诊台，决定哪位专家看哪部分 |
| **Preload** | 把所有条款写成 `Clause` 节点，向量化写入 Qdrant，提取合同主体 | 给专家们准备好病历和参考资料 |
| **LegalResearch** | `LegalResearchAgent` 动态推断适用法律领域，检索法条，生成审查清单 | 先查清楚要依据哪些法律 |
| **Execute** | 多个 Agent 并行审查，先经 RedFlagDetector 红线扫描，再经 CriticAgent 过滤，最后写入图中 | 专家们各自看合同、写诊断 |
| **Merge+Link** | 用法律指纹去重，发现跨条款组合风险，必要时才触发 LLM 兜底 | 主任医师汇总、发现连环问题 |
| **LegalVerify** | 核对每个风险引用的法条是否准确 | 法务复核诊断依据 |
| **Debate** | 对高风险或低置信度项进行正反辩论 | 专家会诊讨论疑难病例 |
| **Triage** | 按严重程度和置信度分类输出 | 最终定级，决定哪些必须改、哪些需复核 |

## 二、前端实现逻辑

### 2.1 技术栈

- **Vue 3** + **TypeScript**：主流前端组合，类型安全、开发体验好。
- **Vite**：前端构建工具，启动快、热更新快。
- **Element Plus / Ant Design Vue** 等 UI 组件库：提供表格、卡片、按钮、弹窗等基础组件。
- **pdf.js**：在浏览器中渲染 PDF，支持原文高亮、划词。
- **EventSource**：接收后端 SSE 实时推送的审查进度。

### 2.2 页面结构

```text
frontend/
├── src/
│   ├── views/          # 页面级组件
│   │   ├── LoginView.vue        # 登录页
│   │   ├── RegisterView.vue     # 注册页
│   │   ├── ContractListView.vue # 合同列表
│   │   ├── UploadView.vue       # 上传合同
│   │   ├── ReviewView.vue       # 审查进度 + 结果报告
│   │   └── AdminView.vue        # 管理后台
│   ├── components/     # 可复用组件
│   │   ├── RiskCard.vue         # 风险卡片
│   │   ├── PdfViewer.vue        # PDF 阅读器
│   │   ├── ReviewProgress.vue   # 审查进度条
│   │   └── ChatPanel.vue        # 对话面板
│   ├── api/            # 后端 API 封装
│   ├── stores/         # Pinia 全局状态
│   └── router/         # Vue Router 路由
```

### 2.3 核心页面交互逻辑

#### 2.3.1 上传合同页

1. 用户拖拽或点击选择合同文件（PDF / Word / 图片）。
2. 前端调用后端 `/api/v1/contracts/upload` 接口上传文件。
3. 上传成功后，后端返回 `contract_id` 和解析出的合同基本信息。
4. 前端跳转到审查进度页。

#### 2.3.2 审查进度页

1. 前端用 `contract_id` 调用 `/api/v1/review/{id}/start` 启动审查。
2. 启动成功后，建立 `EventSource` 连接 `/api/v1/review/{id}/events`。
3. 后端通过 SSE 实时推送每个阶段的状态：
   - `"phase": "route"` → 正在分配任务
   - `"phase": "execute"` → Agent 正在审查
   - `"phase": "completed"` → 审查完成
4. 前端根据收到的消息更新进度条、阶段文字、Agent 状态列表。

#### 2.3.3 审查结果报告页

1. 审查完成后，前端调用 `/api/v1/review/{id}/result` 获取完整结果。
2. 结果包含：
   - 风险统计（高/中/低风险数量）
   - 风险列表（每个风险的等级、条款、描述、法律依据、修改建议）
   - 原文高亮坐标（BBox）
3. 左侧用 `pdf.js` 展示 PDF，根据 BBox 在原文上画框/高亮。
4. 右侧展示风险卡片，点击卡片时 PDF 自动滚动到对应位置并高亮。
5. 支持导出 Word / PDF 报告。

#### 2.3.4 对话页（可选）

1. 用户在 PDF 上划词提问。
2. 前端把选中的文本和上下文发送给 `/api/v1/contracts/{id}/chat`。
3. 后端调用 ChatAgent，基于合同内容流式返回答案。
4. 前端用打字机效果展示回答。

### 2.4 通俗解释

前端就像一个 **合同审查工作台**：

- 上传页 = 把合同放到工作台上。
- 进度页 = 工作台的状态灯，显示"正在排队 / 专家 A 在看 / 专家 B 在看 / 已完成"。
- 报告页 = 工作台最终输出的诊断书，左边是合同原文，右边是问题清单，点哪个问题就跳到原文对应位置。

## 三、后端实现逻辑

### 3.1 技术栈

- **FastAPI**：Python 异步 Web 框架，用于提供 RESTful API。
- **PostgreSQL**：关系型数据库，存用户、合同、审查记录、法条等。
- **Redis**：缓存 + 任务队列 + AgentBus 事件广播。
- **Qdrant**：向量数据库，存法条向量和合同条款向量，支持语义检索。
- **Celery**：异步任务队列，把耗时的审查任务放到后台执行。
- **Alembic**：数据库迁移工具，管理表结构版本。
- **BGE-M3**：中文文本向量模型，用于语义检索。

### 3.2 项目结构


### 3.4 通俗解释

后端就像一个 **合同审查医院的中枢系统**：

- **FastAPI 路由** = 医院的挂号窗口、报告窗口、咨询窗口，对外提供各种服务接口。
- **PostgreSQL** = 医院的档案室，存所有病历（合同）、诊断记录（审查结果）、医生资料（法条库）。
- **Redis** = 医院的广播系统和排队叫号系统，让各科室（Agent）知道谁在做什么、进度如何。
- **Qdrant** = 医院的医学知识搜索引擎，能根据语义找到相关法条和类似病例，而不是只能按关键词查。
- **Celery** = 医院的后台化验室，把耗时的检查任务排队处理，不占用前台资源。

## 四、Agent 实现逻辑

### 4.1 Agent 是什么

Agent 是 **具有特定专业能力的 AI 审查员**。每个 Agent 有自己的专长领域，比如：

- 风险审查专家：识别不公平条款
- 法律专家：为风险找到法律依据
- 合规专家：检查行业特殊规定
- 辩论专家：对高风险项进行正反分析

### 4.2 Agent 架构

```text
┌─────────────────────────────────────────────────────────────┐
│                      ReviewCoordinator                       │
│                   （调度中心，像科室主任）                      │
└──────────────────────┬──────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                        AgentBus                              │
│              （消息总线，像医院广播系统）                       │
└──────────────────────┬──────────────────────────────────────┘
                       │
         ┌─────────────┼─────────────┐
         ▼             ▼             ▼
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │ Agent A  │  │ Agent B  │  │ Agent C  │
   │ 风险审查  │  │ 法条匹配  │  │ 合规检查  │
   └────┬─────┘  └────┬─────┘  └────┬─────┘
        │             │             │
        └─────────────┼─────────────┘
                      ▼
            ┌─────────────────┐
            │   SessionGraph   │
            │  （共享记忆图）   │
            └─────────────────┘
```

### 4.3 SessionGraph：共享记忆图

SessionGraph 是本次审查的 **公共工作台**，所有 Agent 都在上面读写信息。

它由两类东西组成：

1. **节点（Node）**：代表实体
   - `Session`：一次审查会话
   - `Clause`：合同条款
   - `Risk`：发现的风险
   - `Law`：引用的法律条文
   - `Party`：合同主体
   - `Suggestion`：修改建议
   - `Evidence`：证据/依据

2. **边（Edge）**：代表关系
   - `HAS_RISK`：条款包含风险
   - `BASED_ON`：风险基于某法条
   - `RELATES_TO`：条款之间有关联
   - `CONTRADICTS`：条款之间相互矛盾

### 4.4 Agent 列表与职责

| Agent 名称 | 职责 |
|------------|------|
| `TermExtractionAgent` | 提取合同关键商务条款（金额、期限、主体等） |
| `LegalResearchAgent` | 动态推断适用法律领域，检索法条，生成审查要点 |
| `RiskReviewAgent` | 识别不公平、高风险条款；内置 RedFlagDetector 与 CriticAgent |
| `MissingClauseAgent` | 检查合同是否缺少必要条款 |
| `BalanceAgent` | 分析双方权利义务是否对等 |
| `CrossReferenceAgent` | 检查前后条款是否一致 |
| `LegalBasisAgent` | 为风险匹配法律依据 |
| `SuggestionAgent` | 生成具体修改建议 |
| `IndustryComplianceAgent` | 检查行业特殊合规要求 |
| `LegalVerifyAgent` | 验证法条引用是否准确 |
| `DebateAgent` | 对高风险项进行正反辩论 |
| `BlindSpotAgent` | 扫描容易被忽略的盲区 |
| `HumanReviewAgent` | 把低置信度项标记为人工复核 |
| `ChatAgent` | 基于 SessionGraph 回答用户追问 |
| `CriticAgent` | 对候选风险做 RuleCritic + LLM Critic 二次校验，降低误报 |

### 4.5 工具调用机制

每个 Agent 可以调用工具函数获取信息，而不是凭空想象。主要工具有：

| 工具 | 作用 |
|------|------|
| `search_knowledge` | 在法律知识库中检索相关法条 |
| `search_document` | 在合同文档中检索相关条款 |
| `read_section` | 读取指定章节的内容 |
| `output_finding` | 把发现的风险写入 SessionGraph |
| `check_cross_reference` | 检查条款间引用关系 |
| `extract_obligations` | 提取双方权利义务 |
| `validate_calculation` | 验证金额、比例计算是否正确 |
| `compare_with_template` | 与标准模板对比 |
| `query_knowledge_graph` | 查询 Neo4j 法律知识图谱 |
| `web_search` | 联网搜索最新法规和案例 |

### 4.6 八阶段管线详解

#### 阶段 1：Route（路由分配）

Coordinator 扫描每个合同条款，按关键词识别风险信号，给每个 Chunk 分配初始风险等级（`high`/`medium`/`low`）和需要审查它的 Agent 列表。

例如：
- 条款里出现"试用期""社保""竞业限制" → 标记 `high`，派给 RiskReviewAgent、BalanceAgent、LegalBasisAgent；
- 条款里出现"工资""解除""工作地点" → 标记 `medium`，派给 RiskReviewAgent、BalanceAgent；
- 普通格式条款 → 标记 `low`，默认只过 RiskReviewAgent 和 MissingClauseAgent。

#### 阶段 2：Preload（预加载）

1. 把所有条款写成 `Clause` 节点，放进 SessionGraph。
2. 把合同条款向量化，写入 Qdrant，供后续语义检索。
3. 调用 TermExtractionAgent 提取合同主体信息。

#### 阶段 3：LegalResearch（法律研究）

`LegalResearchAgent` 根据合同内容动态推断适用法律领域，检索法条并生成审查要点：

1. 拼接合同文本，调用一次 LLM 同时推断法律领域和风险信号；
2. 对每个法律领域依次执行：本地知识库检索 → 精准联网检索 → 泛化联网检索兜底；
3. 快速路径：当本地+精准检索无结果且风险信号弱时，跳过泛化 web search；
4. 每个合同最多触发 3 次泛化 web search；
5. 生成 `discovered_laws`、`review_checklist`、`risk_signals`，供后续 Agent 使用。

#### 阶段 4：Execute（执行）

多个 Agent 并行运行，每个 Agent 内部是一个 **ReAct 循环**：

```text
观察（Observation） → 思考（Thought） → 行动（Action） → 调用工具 → 再观察
```

以 `RiskReviewAgent` 为例，它内部是"红线扫描 → Critic 校验 → LLM 审查"三层结构：

1. 先调用 `PrincipleBasedDetector` 基于 8 条通用法律原则做快速检查和语义推断，召回明显违法/高风险条款；
2. 对非确定性风险调用 `CriticAgent` 的 RuleCritic（15 条规则）过滤常见误报；
3. 再调用 LLM 逐条审查；若逐条审查产生任何 `high`/`medium` finding，才触发整体性审查，避免在明显合法的合同上浪费全文 LLM 调用。

Agent 发现的风险会写入 SessionGraph，并通过 AgentBus 广播高风险事件。

#### 阶段 5：Merge+Link（合并与关联）

1. **法律指纹去重**：先用 `SessionGraph._legal_fingerprint` 把同一法律问题的不同表述归一化，再在组内通过 clause_text 包含关系、2-gram Jaccard 相似度、clause_ids 交集判断是否重复，合并时保留最高等级和最高置信度。
2. **关联**：建立条款之间的 `RELATES_TO` 边。
3. **冲突**：发现互相矛盾的条款，建立 `CONTRADICTS` 边。
4. **跨条款风险**：先根据 `cross_clause_rules.json`（18 条规则）发现组合风险；仅当规则已命中或图中已存在 `high`/`medium` 风险时，才调用 LLM 兜底补充，避免低风险合同上的无效 LLM 调用。

#### 阶段 6：LegalVerify（法条验证）

LegalVerifyAgent 核对每个风险引用的法条：
- 法条是否真实存在
- 引用是否准确
- 是否过期失效

无法验证的降低置信度，或转人工复核。

#### 阶段 7：Debate（辩论）

对高风险或低置信度项，DebateAgent 进行正反辩论：
- 正方：这是风险，理由是什么
- 反方：这不是风险，或存在例外
- Coordinator 根据辩论结果裁决保留/调整/撤销

#### 阶段 8：Triage（分流输出）

把所有风险按等级和置信度分类：

| 类别 | 处理建议 |
|------|----------|
| 高风险 + 高置信度 | 必须修改 |
| 中风险 | 建议修改 |
| 低风险 | 优化建议 |
| 低置信度 / 组合风险 / Agent 冲突 | 转人工复核 |

最终生成 `findings`（最终风险列表）和 `human_review_items`（人工复核项）。

### 4.7 通俗解释

Agent 系统就像一个 **专家会诊室**：

- **Coordinator** = 科室主任，负责安排流程、协调各位专家、最终拍板。
- **AgentBus** = 广播系统，让专家们能互相看到进展、同步信息。
- **SessionGraph** = 公共白板，所有专家都在上面写诊断意见，互相能看到别人的结论。
- **工具函数** = 专家们手边的参考书和检索系统，查到资料后才能下结论。
- **八阶段管线** = 标准会诊流程：分诊 → 准备资料 → 法律研究 → 各位专家诊断（先红线扫描、再 Critic 校验） → 汇总去重 → 核对依据 → 疑难病例讨论 → 最终定级。

## 五、数据流转总结

```text
用户上传合同
    │
    ▼
后端保存文件 → 解析文本 → 切分 Chunk → 写入 PostgreSQL + Qdrant
    │
    ▼
Celery 启动审查任务 → ReviewCoordinator
    │
    ▼
八阶段 Agent 审查 → 写入 SessionGraph → 通过 AgentBus → Redis → SSE 推送进度
    │
    ▼
审查完成 → 结果写入 review_sessions 表
    │
    ▼
前端拉取结果 → 展示风险卡片 + PDF 高亮 + 报告导出
```

## 六、新人上手建议

1. **先看文档**：`docs/README.md` → `docs/plan.md` → `docs/项目计划.md` → `docs/技术方案.md`。

6. **走一遍完整流程**：上传合同 → 启动审查 → 查看报告，理解数据如何在前后端和 Agent 之间流转。
